**Date:** 2026-09-07 · **Agent:** LIMA · Peter: *"can you please test I2S to the adau1860"*

All figures `[measured]` on the rig unless tagged otherwise. This is the re-verification that
became due when the machine rebooted onto 6.18.39 (see the 2026-09-04 cross-compiler scar).

## Headline: the TX path works on 6.18.39, unchanged from 6.12.47

```
ch=4  requested=3s   exit=0   elapsed=3006 ms      <- first PCM open of the boot
ch=4  requested=5s   exit=0   elapsed=5061 ms
ch=4  requested=3s   exit=0   elapsed=3023 ms
ch=2  requested=3s   exit=0   elapsed=3017 ms
```

`aplay` exits 0 and takes **exactly real time**, which it can only do if the ADAU1860 is generating
the clocks and consuming frames at 48 kHz — the Pi is the consumer and nothing else paces the
transfer. `dmesg` clean, no DMA messages. Card `adau1860-tx` on `1f000a4000.i2s`, which is
`rp1_i2s1` — the consumer block, as the clock-direction scar requires.

## Three things that changed since 2026-09-02, all of which cost time

### 1. The I2C address is **0x67**, not 0x64

`i2cdetect -y 1` shows `0x67`. Every script and note in this directory defaulted to **0x64**; the
address is set by the ADDR1/ADDR0 pins over the range 0x64-0x67. `adau1860_init.py` and
`run_on_pi.sh` defaults corrected in the same commit as this file.

IDs confirm the part: `VENDOR_ID=0x41`, `DEVICE_ID1=0x60`, `DEVICE_ID2=0x18`, `REVISION=0x01` —
which also re-confirms the `[derived]` 32-bit big-endian subaddress framing **on 6.18.39**.

### 2. The machine is called **`aeronode`**, not `scopenode`

`scopenode.local` stopped resolving mid-session. It is the **same machine** — machine-id
`49cc4b68da3b4dfd9d10cc78207fe9eb`, same `~/ardupilot`, same `config.txt.bak-LIMA-*` backups. Its
journal shows the rename happening two seconds into every boot:

```
Sep 07 07:20:58 scopenode systemd[1]: Hostname set to <scopenode>.
Sep 07 07:21:00 aeronode systemd[1]: Listening on systemd-hostnamed.socket ...
```

`/etc/hostname` and `hostnamectl --static` both say `aeronode`; `scopenode` is a transient name at
early boot that no longer survives. **Address it as `192.168.0.99`** — `aeronode.local` failed host
key verification from this Mac and was not chased. Every note in `.agent/` and `linux/` says
"scopenode"; treat that as this machine.

### 3. `pinctrl` sampling is the wrong instrument for a frame clock

Sampling the pins 200 times gave `GPIO18 hi=91 lo=109` (BCLK toggling) but `GPIO19 hi=0 lo=200`,
which reads as "LRCLK is dead". **It is not.** The ADAU1860's frame sync is a *narrow pulse* — at
TDM4 x 32-bit that is 1 BCLK in 128, a 0.8% duty cycle, so 200 random samples are expected to catch
it ~1.6 times and catching it zero times is unremarkable.

`gpiomon` settles it, and the timestamps give the rate directly:

```
GPIO18 (BCLK): rising/falling pairs, sub-microsecond    -> toggling (rate not resolvable, gpiomon
                                                            cannot keep up with 6.144 MHz)
GPIO19 (WS):   falling edges at 20.74 / 20.90 / 20.74 / 20.83 us
               -> 1/20.83 us = 48.0 kHz, and only one edge per frame reported,
                  which is itself the signature of a pulse rather than a 50% duty clock
```

**Generalises:** a level sampler cannot distinguish "dead" from "low duty cycle". If a pin should
carry a clock, count edges — do not sample levels. This is the same failure shape as the
2026-09-04 `pinctrl $4`-vs-`$5` scar: an instrument that returns the answer you expected.

## The discriminator still holds, and it is still the whole game

`SPT0_CTRL1` bit 0 `SAI_MODE`: **1 = TDM fails, 0 = STEREO passes.** Confirmed again on 6.18.39.

| Codec framing | ch | `aplay` | dmesg |
|---|---|---|---|
| `SAI_MODE`=TDM | 4 | `EIO`, `hw_ptr=0` | `dma dma2chan4: failed to stop` |
| `SAI_MODE`=STEREO | 4 | exit 0, real time | clean |

**RP1's DesignWare block requires a 50%-duty frame sync and will not lock to a narrow TDM pulse.**
Setting `dai-tdm-slot-num` on the Linux side does not change what the block locks to.

### New this session: a failed attempt POISONS the boot

After a TDM attempt returns `EIO`, the DMA channel is left stuck — `dma2chan4 is non-idle!` — and
**every subsequent attempt in that boot fails too, including a correct STEREO one.** I switched to
`SAI_MODE=STEREO` in a poisoned boot and still got `EIO`; the same write in a fresh boot passed
first time. The 2026-09-02 note that Run 3 came "after a clean reboot" was load-bearing and I had
read it as incidental.

**So: one framing attempt per boot.** If it fails, reboot before drawing any conclusion from the
next one. A stuck DMA channel is indistinguishable from a configuration fault.

## Method that worked, in order

1. Build + install the overlay, add `dtoverlay=adau1860-pi5-tx` to `config.txt` on its own line.
   Do **not** also set `dtparam=i2s=on` — that enables `rp1_i2s0` (the producer) on the same pins.
2. Reboot. Confirm `aplay -l` shows `adau1860-tx` on `1f000a4000.i2s` and GPIO18-21 are `a4`.
3. Confirm the codec is **cold** — all registers at reset and `STATUS2=0x00`. `CLK_CTRL1`,
   `PLL_PGA_PWR` and `CHIP_PWR` are writable only in this state.
4. `adau1860_init.py --addr 0x67 --fs 48000 --slots 4 --apply` -> `STATUS2=0xF1`
   (`POWER_UP_COMPLETE=1 SPT0_LOCK=1 PLL_LOCK=1`).
5. Set `SPT0_CTRL1 = 0x00` (STEREO) **before the first PCM open of the boot**.
6. `aplay -D hw:0,0 -f S32_LE -c 4 -r 48000 -t raw -d 3 /dev/zero` -> exit 0 in real time.

## Headphone / analog output driven — digital side proven, acoustic side NOT

Peter: *"can you ping the headphone jack of the adau1860 ebz dev board from the pi"*.

Enabled the output path with two writes only — the clock/power trio is already latched correctly in
this boot and rewriting it would MISMATCH (2026-09-02 scar):

```
DAC_ROUTE0     0x4000C053 = 0x00   DAC channel 0 <- Serial Port 0 Channel 0
ADC_DAC_HP_PWR 0x4000C004 = 0x10   PB0_EN=1, DAC + headphone/line-out channel 0 ON
SPT0_CTRL1     0x4000C0E0 = 0x00   STEREO framing (the one RP1 locks to)
STATUS2        0x4000C402 = 0xF1   POWER_UP_COMPLETE=1 SPT0_LOCK=1 PLL_LOCK=1
```

Then played `send_test_pattern.py` output, slot 0 carrying a sine at -12 dBFS:

```
tone1k.raw   (1000 Hz, 6.00 s of 4ch S32_LE)   exit=0   elapsed=6129 ms
tone440.raw  ( 440 Hz, 6.00 s)                 exit=0   elapsed=6130 ms
```

Both real time, `dmesg` clean.

**What this proves:** the Pi transmitted 4,608,000 bytes per file at the codec's own pace, the codec
held `PLL_LOCK`/`SPT0_LOCK` throughout, and the DAC route and output power registers read back
enabled.

**What this does NOT prove, and must not be written up as if it did:** that any analog signal left
the jack. There is no capture path in the playback-only overlay, no loopback, and no instrument on
the output. **Whether the jack makes a sound is Unknown** — it needs ears, a scope, or a meter on
the board. `[fetched]` the UG says the EVAL-ADAU1860EBZ carries a **32 Ω load by default** on P30
and that P16 is a header for external headphone loads, so there is something to measure across.

`[gap]` Two things could still silence a correct-looking configuration, and neither is checkable
from here: a DAC digital volume or mute default (the abridged datasheet carries no register map), and
which serial-port channel the codec actually latches in STEREO framing — the open item from
2026-09-02. If slot 0 is not what reaches DAC channel 0, the output is silence with every register
reading correct.

**To close it properly** — jumper P30 (or P16) back into one of the analog inputs P9/P10/P11, switch
to the duplex overlay, and `arecord` the tone. That turns an unverifiable claim into a measured
one, and it simultaneously settles the slot-latching question: sweep `DAC_ROUTE0` across Serial Port
0 Channel 0/1/2/3 and see which one carries the 1 kHz sine.

To replay on the rig:

python3 ~/send_test_pattern.py --seconds 6 --tone 1000 > ~/tone1k.raw

## Silence explained — and the register-map `[gap]` is CLOSED

Peter reported no sound at P30 across all four `DAC_ROUTE0` settings. Two registers were wrong, and
**neither is visible in the 30-page datasheet** — which is why this sat unexplained since 2026-09-02.

### Where the register map actually lives: ADI's Lark SDK

`[measured]` The abridged datasheet has no register map and `analog.com` is unreachable from here.
But the ADAU1860 mirror carries `related_data/lark_sdk_setup.zip` (4.5 MB) — an NSIS installer whose
payload is **ADI's own C driver source**: `adi_lark_dac.c`, `adi_lark_hpamp.c`, `adi_lark_adc.c`,
`adi_lark_sap.c` and, decisively, the bitfield header `inc/adi_lark_bf_lark_yoda.h`.

Extract without executing it: `7zz x -o<dir> "Lark SDK v3.2.2 Setup.exe"` (`brew install sevenzip`).

The header encodes every bitfield as `ADDRESS, 0x00WWPP` — WW = width, PP = position. That is the
complete register map, from the vendor, with the driver source next to it showing the intended call
order. **This supersedes the `[gap]` in `REGISTER_CONFIG.md` and `DATA_OVER_I2S.md` §3.**

### The two faults

```
DAC_CTRL2   0x4000C051 = 0x44   ->  DAC0_MUTE (bit 6) = 1     THE DAC IS MUTED OUT OF RESET
HPLDO_CTRL  0x4000C066 = 0x00   ->  HPLDO_EN (bit 0)  = 0     HP AMP LDO OFF, NO SUPPLY
```

Everything else was already correct and reading back perfectly — `PB0_EN=1`, `DAC_FS=2` (48 kHz,
matching the data), `DAC0_VOL=0x40` (= +0.00 dB, since dB = 24 - code x 0.375), `DAC0_ROUTE=0`,
`HP0_MODE=0` (headphone), `STATUS2=0xF1`. **A perfectly configured signal path into a muted DAC and
an unpowered output amp looks identical to a working one from the I2C side.**

Fixed:

```
DAC_CTRL2  0x44 -> 0x04   MUTE=0 FORCE_MUTE=0     (keeps DAC_VOL_ZC)
HPLDO_CTRL 0x00 -> 0x01   HPLDO_EN=1
1 kHz @ -3 dBFS, 5 s x2:  exit=0  elapsed 5127 ms, 5127 ms, dmesg clean
```

Both writes are now in `adau1860_init.py`'s `--dac-test` path so this cannot be lost again.

### The lesson, which is the 2026-09-02 scar wearing a new face

That scar says *a register that reads back correctly can still do nothing*. This is the sharper
version: **a whole subsystem can read back correctly and do nothing, because the bit that matters is
in a register you never knew existed.** The defence is not more careful reading of the registers you
know — it is getting the full map. Four hours across two sessions were spent inferring behaviour
from a 30-page abridged datasheet when the vendor ships the authoritative map inside an installer.

**When a datasheet is abridged, go looking for the vendor's SDK, driver source or evaluation
software before designing around the gap.** The map is usually in there.

### Still not closed

Whether the analog output is now audible is **still Peter's to confirm** — I have no instrument on
P30. If it is still silent with `MUTE=0` and `HPLDO_EN=1`, the next reads are `adi_lark_hpamp.c`'s
voltage-mode and LVM settings, and the eval board's own jumpers (P17 selects whether AVDD/HPVDD come
from the on-board 1.8 V LDO at all).

## Sonifying the accelerometer — you can hear what it feels

Peter: *"is it possible to play what accelerometer is feeling"*. Yes. `dsp/vibration-reference/sonify_accel.py`,
MPU-9250 on i2c-2 -> Pi -> I2S -> ADAU1860 DAC -> P30.

**A frequency shift is not optional.** The band on this rig is 3-25 Hz, dominant line 8.30 Hz
(`README_FIR.md`, 2026-09-03). Hearing starts near 20 Hz and a headphone driver does nothing useful
below ~50 Hz, so played straight the accelerometer is **silence**. Two modes, differing in what they
preserve:

| Mode | What it does | Preserves | Real time |
|---|---|---|---|
| `pitch` | capture at fs, emit at 48 kHz -> x48 speed-up; 8.3 Hz lands at **398 Hz** | the spectrum exactly, just scaled — an octave stays an octave | no; 15 s of vibration = 0.31 s of audio, so it loops |
| `live` | high-pass, upsample, multiply by a 1 kHz carrier (DSB); 8.3 Hz becomes 1000 +/- 8.3 Hz | the spectrum, but **mirrored** about the carrier | yes — tap the bench and you hear it |

Both `[measured]` working today:

```
pitch: 15015 samples @ 1000 Hz = 15.0 s, AC rms 3.09 mg, peak 12.49 mg
       -> 6 s of audio, aplay exit=0, 6129 ms
live : 8 s requested, 8977 ms elapsed, no underrun, no FIFO overflow
```

`AC rms 3.09 mg` matches the 2026-09-03 figures (4.79 / 2.45 / 4.13 mg per axis) — **this is a desk,
not a machine.** What you hear is building sway and footsteps. The script says so itself and warns
when the record is essentially still: a near-silent output is a correct result on a quiet bench, not
a broken chain.

**Run it unprivileged.** `node` is in the `i2c` and `audio` groups, and `sudo python3` has no numpy
on this machine while the user's python has 2.5.1. Every earlier script in `linux/adau1860-pi5/`
uses `sudo` unnecessarily.

```
python3 sonify_accel.py --mode live --seconds 30 | \
  aplay -D hw:0,0 -f S32_LE -c 4 -r 48000 -t raw
python3 sonify_accel.py --mode pitch --capture 20 --play 8 | \
  aplay -D hw:0,0 -f S32_LE -c 4 -r 48000 -t raw
```

Useful knobs: `--axis x|y|z|mag`, `--carrier` (live pitch), `--rate` (sensor ODR), `--dbfs`,
`--hpf` (must stay below the band of interest — the default 2 Hz strips gravity and keeps 3-25 Hz).

**Caveat worth keeping in view:** this is the *digital* MPU-9250 on I2C, not an analog accelerometer
into a codec ADC. It proves the audio path and makes the bench audible; it is not the analog
front-end question from `docs/h1-audio-board-codec-selection.md`.
