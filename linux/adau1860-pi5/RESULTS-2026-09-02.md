# Hardware test run, 2026-09-02 — what actually happened

Run by LIMA on `node@192.168.10.34` (`scopenode`), **Raspberry Pi 5 Model B Rev 1.1**, kernel
`6.12.47+rpt-rpi-2712` — the same `rpi-6.12.y` tree the driver analysis was read from.

**Answer to the question asked: no, the samples do not reach the ADAU1860 yet.** Root cause found
and it is a one-bit fix, but applying it needs the board power-cycled. Details below.

## Confirmed working `[measured]`

| Thing | Evidence |
|---|---|
| Chip present and talking | I2C scan of `i2c-1`: **one device, `0x67`** |
| **I2C address is 0x67, not 0x64** | ADDR1=1, ADDR0=1 strapped on your board |
| 32-bit big-endian subaddress | `[derived]` → **confirmed**: `0x41 0x60 0x18 0x01` read back exactly |
| AON block is byte-wide | `[derived]` → **confirmed**: a 4-byte burst from `0x4000C000` returned four consecutive registers |
| Overlay resolves and loads | `dtoverlay -d /tmp adau1860-pi5-tx` → exit 0, **no reboot, `config.txt` untouched** |
| The right RP1 block is selected | `card 2: adau1860tx … 1f000a4000.i2s` — offset **`0xa4000` is `rp1_i2s1`**, the clock **consumer** |
| Pin muxing | `pinctrl`: GPIO18-21 → `I2S1_SCLK / I2S1_WS / I2S1_SDI0 / I2S1_SDO0` |
| GPIO18-21 were free | unclaimed before the overlay loaded — no conflict with your existing AeroNode overlays |
| TDM4 / 32-bit / 48 kHz accepted | `aplay -v`: `format S32_LE, channels 4, exact rate 48000` negotiated cleanly |
| Register writes land | every SPT0 write read back correctly |

So the entire Linux-side analysis held up on real hardware, first time.

## The failure `[measured]`

```
aplay: pcm_write:2178: write error: Input/output error
  ... appl_ptr: 0 / hw_ptr: 0
dmesg: dma dma2chan4: dma2chan4 failed to stop
```

The PCM configures perfectly and then **not one frame moves**. Proof of why — overlay unloaded,
GPIO18/19 set as inputs, sampled 200 times each:

```
GPIO18: hi=0 lo=200        <- BCLK dead
GPIO19: hi=0 lo=200        <- LRCLK dead
```

**The ADAU1860 is not generating clocks.** In consumer mode the Pi cannot tell you that — exactly
the silent failure mode called out in `DATA_OVER_I2S.md` §7.

## Root cause — and it was my bug

`PLL_PGA_PWR` (`0x4000C005`) bit 0 is **`PLL_EN`**, and its reset value `0x02` leaves it **0**.
I had flagged this register as a `[gap]` and shipped an init sequence that never set it. With the
PLL off, the BCLK/LRCLK generators have no source to divide, so `SPT0_CTRL2 = 0x02` ("generate
6.144 MHz") does nothing at all — the register reads back correctly and produces no clock.

**The hardware is fine, and I proved it.** During a permutation sweep, this combination:

```
CLK_CTRL1    = 0xC8   (XTAL_MODE=1, crystal)
PLL_PGA_PWR  = 0x03   (XTAL_EN=1 | PLL_EN=1)
CHIP_PWR     = 0x07
```

gave **`STATUS2 = 0xF1` → POWER_UP_COMPLETE=1, PLL_LOCK=1, SPT0_LOCK=1.** There is a working
crystal on your board and the part locks to it. Your board can be BCLK master.

## Why it is now stuck, and what is needed

`[measured]` Once the power domains come up, **`CLK_CTRL1`, `PLL_PGA_PWR` and `CHIP_PWR` all go
read-only.** Writes are accepted without error and the readback never changes:

```
0x4000C010 <= 0xC8  readback 0xC0  MISMATCH
0x4000C005 <= 0x03  readback 0x00  MISMATCH
0x4000C00E <= 0x00  readback 0x07  MISMATCH
```

`SOFT_FULL_RESET` (`RESETS` `0x4000C200` bit 0) **does not clear them** — tried, no effect. Dropping
through Hibernate0/1/2 does not either; `CHIP_PWR` refuses all four values.

**The part cannot be reset over I2C at all.** `[measured]` All three variants of the `RESETS`
register were written and every one was ACKed by the chip:

| Write | ACK | `CHIP_PWR` | `CLK_CTRL1` | `PLL_PGA_PWR` | `STATUS2` |
|---|---|---|---|---|---|
| `0x01` `SOFT_FULL_RESET` | yes | `0x07` | `0xC0` | `0x00` | `0xF0` |
| `0x10` `SOFT_RESET` | yes | `0x07` | `0xC0` | `0x00` | `0xF0` |
| `0x11` both | yes | `0x07` | `0xC0` | `0x00` | `0xF0` |

Each was followed immediately by 40 back-to-back writes of `CLK_CTRL1`/`PLL_PGA_PWR` with no delay,
to catch any brief window before the registers re-latch. Nothing moved. **A future session should
not spend time on a software reset path — there isn't one.**

> **Needed: a power cycle of the ADAU1860** (or a `PD` pin toggle). I cannot do that over SSH.
> If `PD` or a supply enable is on a Pi GPIO, tell me which and I will do it myself.

After the power cycle, `adau1860_init.py` now writes the clock config **before** `CHIP_PWR`, which
is both the fix and the order UG-2257's own power-up sequence gives (step 5 clocks, step 7 verify).
It also prints `STATUS2` and says plainly when `PLL_LOCK=0`.

## On "I'm using I2S0"

If you mean **the ADAU1860's serial port 0** — that is what is configured (`SPT0_*`), we agree.

If you mean **the Pi's I2S0**, that contradicts codec-master and would be the next bug. On Pi 5 both
`rp1_i2s0` and `rp1_i2s1` can drive GPIO18-21; the choice *is* the clock direction:

- `rp1_i2s0` = `i2s_clk_producer` — **the Pi drives BCLK/LRCLK**
- `rp1_i2s1` = `i2s_clk_consumer` — **the codec drives them** ← what you asked for, what is loaded

`dwc-i2s.c` sets `DW_I2S_MASTER` or `DW_I2S_SLAVE` exclusively from a synthesis parameter and
rejects the opposite format, so "Pi on I2S0" and "ADAU1860 is BCLK master" cannot both be true.
`pinctrl` confirms the loaded overlay put the pins on **I2S1**.

## On "make sure the ADAU1860 is master BCLK"

It is, in configuration, and the registers read back correct:

| Register | Value | Meaning |
|---|---|---|
| `SPT0_CTRL2` `0x4000C0E1` | `0x02` | `BCLK_SRC=010` — **generate** 6.144 MHz |
| `SPT0_CTRL3` `0x4000C0E2` | `0x01` | `LRCLK_SRC=0001` — **generate** 48 kHz |

Master on this part is not a bit — it is "generate" versus "external" on those two fields, and both
are set to generate. The configuration is right. What is missing is the source clock the generators
divide down, which is the `PLL_EN` bug above.

## Left on the bench

The ADAU1860 currently has `SPT0` configured, `DAC_ROUTE0 → SPT0 ch0`, `PB0_EN` on, and is wedged
with `PLL_LOCK=0`. All of it is volatile — the power cycle clears the lot. The Pi's `config.txt` was
**not modified** and the overlay was loaded at runtime, so a reboot returns the Pi to exactly its
prior state. `/tmp` holds the scripts.

# Run 2 — after the power cycle

**The codec side is now completely working.** `[measured]`

Clean reset confirmed first: IDs `0x41 0x60 0x18 0x01`, and `CHIP_PWR` `0x00`, `CLK_CTRL1` `0xC8`,
`PLL_PGA_PWR` `0x02`, `STATUS2` `0x00` — every register at its documented reset value.

With the corrected order (clocks before `CHIP_PWR`, `PLL_EN` set), **every write took**, and:

```
STATUS2 0x4000C402 = 0xF1   POWER_UP_COMPLETE=1  SPT0_LOCK=1  PLL_LOCK=1
```

**And the clocks are physically on the pins.** Overlay unloaded, GPIO18/19 as inputs, 200 samples:

| Codec mode | GPIO18 (BCLK) | GPIO19 (FSYNC/LRCLK) | Reading |
|---|---|---|---|
| TDM4, `SPT0_CTRL1=0x01` | hi=89 lo=111 | **hi=2 lo=198** | ~1% high — a narrow pulse once per 128-BCLK frame. **TDM framing.** |
| Stereo I2S, `SPT0_CTRL1=0x00` | hi=109 lo=91 | **hi=114 lo=86** | ~50% — a square wave. **I2S framing.** |

That the FSYNC duty cycle changes from 1% to 50% exactly when `SAI_MODE` is toggled is independent
confirmation that the part is doing precisely what it is told, on the wire. **The ADAU1860 is a
working BCLK and LRCLK master.** The `PLL_EN` fix was the whole story on the codec side.

## What is still failing, and it has moved

With clocks confirmed running, TDM4 playback **still** returns `EIO` with `hw_ptr=0` and
`dma dma2chan4: dma2chan4 failed to stop`. The codec reads back perfect throughout
(`STATUS2=0xF1`, all `SPT0_*` correct). **So the remaining fault is on the Pi side, not the codec.**

The most likely candidate, untested: **the RP1 DesignWare block may not accept a narrow-pulse TDM
frame sync.** DesignWare I2S is natively a stereo part with a 50%-duty LRCLK; its "TDM" is built
from stacked stereo channel blocks. This is consistent with the February 2026 CM5 forum report of
I2S1 slave mode failing to detect an external clock.

**The next test is therefore plain stereo I2S** — 2 slots, 3.072 MHz BCLK, 50% LRCLK — which is the
simplest configuration that answers Peter's actual question. The codec is already switched to it and
its clocks verified (table above).

## Blocked on a reboot `[measured]`

Repeated `dtoverlay -r` / re-load cycles have left ASoC unable to re-register the card. The overlay
reports as loaded (`dtoverlay -l` shows `adau1860-pi5-tx slots=2`) but no card appears in `aplay -l`.
Removing and reloading `snd_soc_simple_card`, `snd_soc_simple_card_utils`, `snd_soc_spdif_tx` and
`designware_i2s` does **not** bring it back — the overlay's DT nodes do not fully unwind, which is
what the kernel's own `OF: overlay: WARNING: memory leak will occur if overlay removed` warnings are
telling us.

> **Runtime overlay loading is fine once; repeated unload/reload of a sound-card overlay is not.**
> Budget a reboot per configuration change, or put the overlay in `config.txt` while iterating.

`scopenode` needs a reboot to continue. It has no containers running and a load average of 0.02, but
**a second SSH session is connected** (from `100.64.0.4`, since 13:42), so I have not rebooted it.
`config.txt` is still unmodified, so the Pi comes back exactly as it was, without the overlay.
