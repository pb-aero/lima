## Piper install — what the current project actually is

The original `rhasspy/piper` went read-only in October 2025 and relicensed MIT -> GPL-3.0;
active development is **`OHF-Voice/piper1-gpl`** under the Open Home Foundation. `[fetched]`
PyPI `piper-tts` **1.8.0** (2026-09-04) publishes a
`cp39-abi3-manylinux_2_28_aarch64` wheel — **abi3, so it installs on Python 3.13 with no
compilation**, which is the thing that usually breaks this on a current Debian.

Installed into a **venv** (`~/piper-venv`), not `--break-system-packages`. Debian 13 marks its
Python externally-managed (PEP 668), and this box's system Python carries the ArduPilot
toolchain — letting onnxruntime/numpy/protobuf overwrite distro packages under a flight-software
build is a trade with no upside. Reproduced by `install_piper.sh`, which is idempotent
(second run: `have <voice>` x3, no re-download).

Pulled in: `onnxruntime 1.29.0`, `numpy 2.5.3`, `protobuf 7.36.1`, `flatbuffers`, `pathvalidate`.

## The pipeline, and the one leg that could lie

```
piper --output-raw          mono S16_LE at the MODEL's rate
  | ffmpeg -af aresample=soxr  -> mono S32_LE at 48 kHz
  | pack_slots.py              -> 4 slots, audio in 0 and 2
  | aplay -c 4                 -> I2S -> ADAU1860 DAC -> P30
```

**The model rate is read from `<voice>.onnx.json`, never assumed.** Medium voices are 22050 Hz
(`config sample_rate = 22050` `[measured]`), but the low/high tiers differ, and handing ffmpeg the
wrong input rate is a **pitch shift that sounds like a working system** — an error with no failure
mode to trip over. This is §3's "verify at the point of use" applied to a number, not a control.

**Slot packing is not optional.** Only slots 0 and 2 survive the wire (`91b0e9e`: RP1 will not
lock to the narrow TDM sync, so the codec runs `SAI_MODE=STEREO` and takes one 32-bit word per
LRCLK edge). Mono goes to **both** so both codec channels get it; `aplay` is still told `-c 4`
because the transport stays four words wide whatever lands.

**Gain is fixed at -6 dBFS, not peak-normalised** — a streaming packer has no future to measure.
Piper normalises its own output, so this is a straight halving, with headphones downstream.

**Neither script writes a codec register.** `bringup.sh` from a cold board owns that. One framing
attempt per boot is the rule and a second attempt fails in a poisoned boot however correct it is.

## Voices installed

`en_GB-alba-medium` (default), `en_US-lessac-medium`, `en_GB-northern_english_male-medium` —
~63 MB each in `~/piper-voices`. `piper.download_voices` with no argument lists the full catalogue
(30+ languages, 100+ voices). `[fetched]`

**Download gotcha:** the `.onnx` lands before the `.onnx.json`. A directory listing mid-download
shows a plausible-looking `12M .onnx` with no sibling json — **the json's absence is the honest
completion check**, and one of the three needed a re-run after a timeout truncated it.

## CLOSED by ear — the analog output works

**Peter heard all three voices** `[measured, by ear]` — the one instrument this bench has and the
only one that could settle it. Speech is intelligible out of P30, so the chain is proven end to
end: neural synthesis on the Pi -> soxr resample -> slots 0 and 2 -> I2S -> ADAU1860 DAC -> analog.

Everything else in this document measures only the *digital* path — bytes clocked out at the
codec's pace with the locks held — and that was never sufficient. It stayed **Unknown** across six
days and four sessions for a good reason: on 2026-09-07 a **muted DAC and an unpowered headphone
LDO read back perfectly over I2C** while producing silence. So the caveat retires for *this*
configuration only. A new route, a new power state or a fresh cold boot still needs ears.
