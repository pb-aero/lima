## The finding: `include` inherits sensors, and `undef` will not remove them

The obvious way to write this target is `include ../pi5/hwdef.dat`, since `pi5` already carries the
native toolchain, the RP1 GPIO backend and the board subtype. That is what I wrote first, and it
produces a target that is **wrong in a way `configure` reports as success**.

`configure` finished cleanly. The generated `build/aeronode/hwdef.h` said this `[measured]`:

```c
#define HAL_INS_PROBE1  ADD_BACKEND(AP_InertialSensor_Invensense::probe(*this,GET_I2C_DEVICE(2,0x68),ROTATION_ROLL_180))
#define HAL_INS_PROBE2  ADD_BACKEND(AP_InertialSensor_Invensensev3::probe(*this,hal.spi->get_device("icm45686"),ROTATION_NONE))
#define HAL_INS_PROBE_LIST HAL_INS_PROBE1;HAL_INS_PROBE2
```

The pi5 dev rig's **MPU-9250 on `i2c-2:0x68`** came along, as PROBE**1**, with the AeroNode IMU
appended behind it — and so did the AK8963 compass and the LPS22HB baro. `undef HAL_INS_DEFAULT`
and `undef INS_MAX_INSTANCES` do nothing about it: the generator **appends** device lines, and
`undef` only touches `define`s. Worse, with `INS_MAX_INSTANCES 1` and two probes in the list, the
one real AeroNode IMU is the one that would have been dropped.

An AeroNode flight controller that probes an address on a bus that does not exist on AeroNode, and
that silently prefers it to the sensor that does — from a `configure` that printed
`finished successfully`. This is the shape of failure `CLAUDE.md` §3 exists for: **verify at the
point of use.** The point of use here is the generated header, not the exit code.

**The fix:** inherit `../linux/hwdef.dat` and re-add the two pi5 lines by hand.

```
include ../linux/hwdef.dat
define HAL_LINUX_GPIO_RPI_ENABLED 1
define CONFIG_HAL_BOARD_SUBTYPE HAL_BOARD_SUBTYPE_LINUX_PI5
```

### The one-command CM5 test, with its expected bytes measured

`Util_RPI.cpp` switches on the peripheral base address in `/proc/device-tree/soc*/ranges`; `0x10`
means `RPI_5` and anything else means `UNKNOWN_BOARD`, which is an `AP_HAL::panic` at startup on a
target with the RPi GPIO backend enabled. On the Pi 5 `[measured]`:

```
$ od -An -tx1 -N16 /proc/device-tree/soc*/ranges
 00 00 00 00 00 00 00 10 00 00 00 00 80 00 00 00
```

Bytes 4–7 are `00 00 00 10`. **Run that same command on the CM5 and compare.** If it matches, the
whole Pi 5 groundwork applies unchanged. `[assumed]` it will — same BCM2712 — but that is exactly
the kind of expectation a broken instrument confirms too neatly, so measure it before believing it.

## Prerequisite that is still not filed

The target enables the RP1 GPIO backend, so it **requires** the `Util_RPI.cpp` soc-node prefix fix
(`strncmp(d_name,"soc",4)` → `3`). Every 2712-class kernel names the node `soc@107c000000`, so
unpatched upstream detects `UNKNOWN_BOARD` and panics. That patch is in
`../ardupilot-pi5/upstream-pr/` and is **still unfiled** — no fork at `pb-aero/ardupilot`, no `gh`
in this fleet.

## What this result does NOT establish

- **No sensor has been read.** The Pi 5 has only `/dev/spidev0.0` and `/dev/spidev10.0`
  `[measured]`; nothing answers to `icm45686` or `rm3100` there. This is a build result.
- **Every bus number in the hwdef is a placeholder.** The AeroNode design still has no CM5 sensor
  sheet, so which part sits on SPI3, SPI4 or I2C1 is unrecorded. The numbers were chosen so the
  target parses; they carry no design authority. `LINUX_SPIDEV`'s bus/subdev are Linux spidev
  enumeration numbers under the carrier's overlay config, not the SoC's block numbers.
- **Every `ROTATION_NONE` is a placeholder** asserting level-and-forward mounting.
- **An instrument lied first, and it was mine.** The first build failed on `dronecangen` with
  `ModuleNotFoundError: No module named 'em'`, which reads like a missing dependency. It was not:
  `configure` had been run outside `~/venv-ardupilot`, so waf cached `/usr/bin/python3` and never
  saw the venv's `empy`. Re-running `configure` **inside** the venv fixed it with no install.
  Activate the venv before `configure`, not just before `build`.
