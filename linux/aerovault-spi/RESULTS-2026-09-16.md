## The part is not there `[measured]`

```
JEDEC ID (9Fh + dummy) : 00 00 00   expected EF AA 21
```

Then the discriminating test — enable the Pi's internal pull-up on MISO (GPIO9) and read again:

```
JEDEC ID (9Fh + dummy) : FF FF FF
```

**MISO is undriven.** A powered W25N01GV with CS asserted would drive that line during the ID read
and return `EF AA 21` regardless of the pull-up; instead the line simply follows whatever the Pi
does with it — 0x00 floating, 0xFF pulled up. So: the click board is **not connected, not powered,
or its DO line is open.** Pull-up restored to `pn` afterwards.

**Control, so this is a finding and not a broken instrument:** the same bus, same session, same
`spidev0.0` — `SPI_LOOP` internal loopback still echoes byte-clean to 50 MHz. The controller, the
driver, the ioctl path and the CS are all working. Only the part is missing.

### CORRECTION to this morning's entry

I wrote that the pull-up test showed **"MISO is open."** That was over-stated and I am retracting
the *specific* claim. The W25N's `DO` pin is high-Z whenever `/CS` is high, so a correctly wired,
powered part would ALSO let GPIO9 follow the Pi's internal pull — the test cannot tell an open wire
from a silent chip. What is proven, now that CS is confirmed asserting, is the weaker and more
useful statement: **during a read with `/CS` low, nothing drives MISO.** Which wire or which rail is
at fault is not determined from here.

I also briefly recorded "CS never goes low" from a 14-sample run. **That was my instrument, not the
Pi** — the samples all completed in ~0.2 s while the Python transfer process was still importing
`spidev`, so every sample landed before the bus was busy. Sampling during the transfer gives
200/200 low. Exactly the §3 failure mode: a broken measurement that agreed with what I suspected.

### For Peter, in order of likelihood

1. **GND.** The most common flying-lead miss, and it fails exactly like this.
2. **3V3 to the click board.** Flash 5 Click is a 3.3 V part; mikroBUS also carries 5 V, and the
   3V3 rail is the one this needs.
3. **`SDI`/`SDO` crossed.** `[assumed]` — mikroBUS silkscreens name data lines from the *click
   board's* point of view, so its `SDI` takes the Pi's **MOSI** (GPIO10, pin 19) and its `SDO`
   drives the Pi's **MISO** (GPIO9, pin 21). Reading those labels as if they were the Pi's is the
   classic way to cross them, and a crossed pair produces precisely this symptom — the part never
   receives a command, so it never drives anything back.
4. CS → GPIO8 (pin 24), SCK → GPIO11 (pin 23). Both confirmed live from the Pi side.
