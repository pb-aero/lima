# ADAU1372 on aeronode — state of play, 2026-09-17

Written after a long session. Sorted into what is proven, what I retracted, and what is left.

## Proven, with the evidence

| Claim | Evidence |
|---|---|
| The part is an ADAU1372 at I2C 0x3C | 6 of 7 datasheet reset values read back exactly |
| Control port works | write/readback, gated by MCLK exactly as the datasheet says, with a clean negative control |
| Oscillator is 12.288 MHz | 480000 frames in 10.029 s = 47,862 Hz; **and** UG-807 states a 12.288 MHz crystal |
| Codec generates BCLK/LRCLK, Pi locks | GPIO18/19 went from stuck-low to 39/41 and 41/39; captures run with no XRUN or EIO |
| Mainline driver runs it | built out-of-tree (RPi OS does not ship `snd-soc-adau1372`), `card 1: adau1372`, 50 ALSA controls |
| Power is correct | Peter confirmed J8, J10, J12, **J17 (AVDD)** all fitted; J15 (/PD) clear |
| **The DAC works** | Peter heard tones on J23, repeatedly, at several levels |
| Serial output slots carry data | serial-input -> serial-output loopback returns real tones |
| **The ADC returns mathematically exact zeros** | every condition tried, see below |

## The ADC result, and why it is strange

Exact zeros — not noise, not a DC offset, not garbage — on all four channels, under every one of:

- hand-written register configuration, and the mainline driver's own initialisation
- PGA disabled (single-ended line mode) and PGA enabled at 0 dB and at +35.25 dB
- open input, and **a real 1 kHz analog signal driven into J18** from the USB dongle's headphone output
- every register verified live *during* the stream: `ADC_CTRL0=0x01 ADC_CTRL2=0x23 ASRC_MODE=0x02
  DECIM_PWR=0xFF PGA0=0xBC SOUT_CTRL=0xF0 MODE_MP1=0x00 SAI_0=0x20 SAI_1=0x11`
- DAPM reporting the whole chain `On` mid-capture: AIN0 -> PGA0 -> ADC0 -> ADC0 Filter ->
  Decimator0 Mux -> Output ASRC Supply -> Output ASRC0 Mux -> Serial Output 0 Capture Mux -> Capture

The datasheet's two "easy to miss" requirements are both satisfied: `ADC_x_EN` (ADC_CONTROL2/3) and
the `SYNC_x_EN` bits in `DECIM_PWR` which it says "must be enabled along with" them.

**Exact zeros is a digital signature, not an analog one.** A converting ADC with a floating input and
+35 dB of gain cannot produce them; it produces noise. And the same serial port, slots and mux that
deliver zeros from the ADC path deliver real audio when sourced from the serial inputs. So the zeros
are being produced inside ADC -> decimator -> output ASRC, and every documented enable in that path
is set.

## Separately broken: TDM slot alignment

The digital loopback with a distinct tone per slot returns a **non-deterministic** map — three
consecutive runs gave ch0 = slot 3 / slot 0 / slot 3 — with tones mixed across slot boundaries, every
peak clipping to +-2^31, and only 2 of 4 channels ever carrying data. Tried and did **not** fix it:
`frame-inversion` (LR_POL = 1, verified `SAI_1 = 0x11`), 2-channel instead of 4, and dropping BCLK
from 6.144 MHz to 1.024 MHz (which rules out signal integrity). A bit-offset search over all 128
frame positions found no constant shift, so the framing is not stable within a single capture.

This is a real and separate fault from the ADC silence.

## Retracted this session

1. **"RP1 locks to the ADAU1372's TDM4 frame."** It streams without XRUN; it is not slot-aligned.
2. **"The transport is proven end to end."** The loopback moved bytes, not the right bytes. The tell
   was there and I missed it: a −8 dBFS tone returning at −0.5 dBFS is not a working path.
3. **"Talkthrough is silent, so the ADC is dead."** The instrument was invalid — I toggled *mute*
   bits to make a test sound, and muting silence is silent. It could never have worked.
4. **"The DAC output is a sawtooth, so the data is bit-shifted."** Measured through a USB dongle that
   turned out not to be recording the codec at all: its level tracked its own capture gain and was
   independent of the signal across 30 dB. Every number from it is void.
5. **`0xB8 = 1` might power the target down.** AN-1006 Figure 24 says `USB_PWR_ON` turns the
   transistors on when driven high, and ADI's default is on.

The common thread in 3, 4 and 5 is trusting an instrument I had not validated. The rule that would
have caught all three: before believing a negative result, prove the measurement can produce a
positive one.

## What I would do next, in order

1. **Meter on AIN0 (codec pin 9), board powered.** It should sit near AVDD/2 (~1.65 V with a 3.3 V
   AVDD). If it does, the analog front end is biased and alive and the fault is digital. If it sits
   at 0 V or at a rail, that is the answer. This is the one measurement that cannot be done remotely
   and has not been done.
2. **Run the board from SigmaStudio over the USBi**, on a Windows PC, and capture with ADI's own
   configuration. This removes my register sequence *and* the Linux driver from the question
   entirely. If the ADCs work under SigmaStudio, the fault is in how the part is being driven and I
   can diff the register maps; if they do not, it is the board or the part.
3. Only then return to the TDM slot alignment, which needs a known-good ADC signal to diagnose
   properly — a loopback cannot settle it because both directions are suspect at once.
