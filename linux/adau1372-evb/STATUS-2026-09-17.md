# ADAU1372 on aeronode — state of play, 2026-09-17

Written after a long session. Sorted into what is proven, what I retracted, and what is left.

## Proven, with the evidence

| Claim | Evidence |
|---|---|
| The part is an ADAU1372 at I2C 0x3C | 6 of 7 datasheet reset values read back exactly |
| Control port works | write/readback, gated by MCLK exactly as the datasheet says, with a clean negative control |
| Oscillator is 12.288 MHz | 480000 frames in 10.029 s = 47,862 Hz; **and** UG-807 states a 12.288 MHz crystal |
| Codec generates BCLK/LRCLK, Pi locks | GPIO18/19 went from stuck-low to 39/41 and 41/39; captures run with no XRUN or EIO |
| Mainline driver runs it | built out-of-tree (RPi OS does not ship `snd-soc-adau1372`), `card 1: adau1372`, 50 ALSA controls |
| Power is correct | Peter confirmed J8, J10, J12, **J17 (AVDD)** all fitted; J15 (/PD) clear |
| **The DAC works** | Peter heard tones on J23, repeatedly, at several levels |
| Serial output slots carry data | serial-input -> serial-output loopback returns real tones |
| **The ADC returns mathematically exact zeros** | every condition tried, see below |

## The ADC result, and why it is strange

Exact zeros — not noise, not a DC offset, not garbage — on all four channels, under every one of:

- hand-written register configuration, and the mainline driver's own initialisation
- PGA disabled (single-ended line mode) and PGA enabled at 0 dB and at +35.25 dB
- open input, and **a real 1 kHz analog signal driven into J18** from the USB dongle's headphone output
- every register verified live *during* the stream: `ADC_CTRL0=0x01 ADC_CTRL2=0x23 ASRC_MODE=0x02
  DECIM_PWR=0xFF PGA0=0xBC SOUT_CTRL=0xF0 MODE_MP1=0x00 SAI_0=0x20 SAI_1=0x11`
- DAPM reporting the whole chain `On` mid-capture: AIN0 -> PGA0 -> ADC0 -> ADC0 Filter ->
  Decimator0 Mux -> Output ASRC Supply -> Output ASRC0 Mux -> Serial Output 0 Capture Mux -> Capture

The datasheet's two "easy to miss" requirements are both satisfied: `ADC_x_EN` (ADC_CONTROL2/3) and
the `SYNC_x_EN` bits in `DECIM_PWR` which it says "must be enabled along with" them.

**Exact zeros is a digital signature, not an analog one.** A converting ADC with a floating input and
+35 dB of gain cannot produce them; it produces noise. And the same serial port, slots and mux that
deliver zeros from the ADC path deliver real audio when sourced from the serial inputs. So the zeros
are being produced inside ADC -> decimator -> output ASRC, and every documented enable in that path
is set.

## Separately broken: TDM slot alignment

The digital loopback with a distinct tone per slot returns a **non-deterministic** map — three
consecutive runs gave ch0 = slot 3 / slot 0 / slot 3 — with tones mixed across slot boundaries, every
peak clipping to +-2^31, and only 2 of 4 channels ever carrying data. Tried and did **not** fix it:
`frame-inversion` (LR_POL = 1, verified `SAI_1 = 0x11`), 2-channel instead of 4, and dropping BCLK
from 6.144 MHz to 1.024 MHz (which rules out signal integrity). A bit-offset search over all 128
frame positions found no constant shift, so the framing is not stable within a single capture.

This is a real and separate fault from the ADC silence.

## Retracted this session

1. **"RP1 locks to the ADAU1372's TDM4 frame."** It streams without XRUN; it is not slot-aligned.
2. **"The transport is proven end to end."** The loopback moved bytes, not the right bytes. The tell
   was there and I missed it: a −8 dBFS tone returning at −0.5 dBFS is not a working path.
3. **"Talkthrough is silent, so the ADC is dead."** The instrument was invalid — I toggled *mute*
   bits to make a test sound, and muting silence is silent. It could never have worked.
4. **"The DAC output is a sawtooth, so the data is bit-shifted."** Measured through a USB dongle that
   turned out not to be recording the codec at all: its level tracked its own capture gain and was
   independent of the signal across 30 dB. Every number from it is void.
5. **`0xB8 = 1` might power the target down.** AN-1006 Figure 24 says `USB_PWR_ON` turns the
   transistors on when driven high, and ADI's default is on.

The common thread in 3, 4 and 5 is trusting an instrument I had not validated. The rule that would
have caught all three: before believing a negative result, prove the measurement can produce a
positive one.

## What I would do next, in order

1. **Meter on AIN0 (codec pin 9), board powered.** It should sit near AVDD/2 (~1.65 V with a 3.3 V
   AVDD). If it does, the analog front end is biased and alive and the fault is digital. If it sits
   at 0 V or at a rail, that is the answer. This is the one measurement that cannot be done remotely
   and has not been done.
2. **Run the board from SigmaStudio over the USBi**, on a Windows PC, and capture with ADI's own
   configuration. This removes my register sequence *and* the Linux driver from the question
   entirely. If the ADCs work under SigmaStudio, the fault is in how the part is being driven and I
   can diff the register maps; if they do not, it is the board or the part.
3. Only then return to the TDM slot alignment, which needs a known-good ADC signal to diagnose
   properly — a loopback cannot settle it because both directions are suspect at once.

# 64 fs framing — Peter's call, and it fixed the link

`[measured]` 2026-09-17, after Peter pointed out that the codec is the clock master and **the Pi
needs a 64 fs LRCLK**. The codec had been framing TDM4 = 128 BCLK per frame while the RP1 I2S block
wanted 64. That mismatch was the whole slot-map problem.

Overlay changed to plain stereo I2S: every `dai-tdm-slot-*` property removed (so the driver never
calls `set_tdm_slot`, leaving `SAI` in I2S mode and `SOUT_CONTROL0` at 0x00), and `frame-inversion`
removed. Verified after reboot: **`SAI_0 = 0x00`** (was 0x20 = TDM4), `SAI_1 = 0x01`.

## The loopback is now bit-exact

Sending 0.25 FS tones and reading the raw samples back:

```
sent  0.25 x 2^31 = 536870911 = 0x1FFFFFFF
ch1   0, +-205451603, +-379625062, +-496004046, +-536870911
```

Those are exactly `0.25 x 2^31 x sin(2*pi*k/16)` for 3 kHz at 48 kHz — the transmitted values,
sample for sample. ch0's 250 Hz is likewise a clean ramp. **The slot map is correct and
deterministic**, where TDM4 gave a different answer on every run.

`[correction]` I first reported this run as "purity 13-22%, peaks pinned to +-2^31, still corrupt".
That came from summary statistics over a window containing the corrupt samples below; looking at the
raw values instead showed the stream is bit-perfect apart from them. Summary statistics hid the
answer that one `print` of the actual numbers made obvious.

## Residual: 0.2% of samples corrupt, and it is mains-synchronous

| | |
|---|---|
| corrupt samples | 197 of 96000 on ch1, 233 on ch0 — **~0.2%**, about 1 in 450 |
| nature | garbage values substituted into an otherwise exact sine, not a shift or a scale |
| **periodicity** | **960 samples = exactly 20 ms = 50 Hz**, with two events per cycle (gaps of 224 and 736, which sum to 960) |
| independent of ALSA | the 960 spacing is unchanged at `--period-size` 480, 960 and 1920, so it is **not** the host DMA or period handling |

20 ms periodicity on a digital link is mains. This is EMI picked up on the I2S wiring — short leads
with proper ground returns are the fix, the same lesson the AeroVault SPI-NAND work landed on.

`[correction]` Earlier I wrote that dropping BCLK from 6.144 MHz to 1.024 MHz "rules out signal
integrity". It ruled it out for the **slot map** (which was the framing bug Peter spotted). It said
nothing about occasional bit errors, and this 50 Hz signature shows signal integrity is a live issue
after all.

## Still open: the ADC reads exact zeros

Unchanged by the framing fix. With the link now proven bit-exact in loopback, an ADC signal would
come through cleanly if it existed. The untested link in the chain remains **whether any signal
reaches AIN0** — the dongle jack arrangement was never resolved, and every ADC test has depended on
it.

**Next: patch the codec's own stereo out (J23) into J18.** The DAC is proven by ear, it is
board-to-board with no connector ambiguity, and both ends can be driven from here. That answers the
ADC question without depending on anything unverified.

# Analog loopback (J23 -> J18): the ADC works, its data path is corrupt

`[measured]` 2026-09-17. Codec DAC -> J23 -> J18 -> AIN0 -> codec ADC -> I2S -> Pi. Both ends are the
same chip; the DAC is proven by ear and the serial link is proven bit-exact.

## The ADC is alive — this retires the biggest open question

Identical full-duplex conditions, only the DAC content changed:

| DAC plays | capture |
|---|---|
| **digital silence** | **exact zeros** |
| **1 kHz** | **nonzero, ~-20 dBFS** |
| 1 kHz (repeat) | nonzero, -19.5 dBFS |

The capture tracks the analog input. **The ADC converts.** Every "exact zeros" result earlier today
was what it appeared to be: no signal reaching AIN0. The input was an open-ended cable, and then a
USB dongle whose jack arrangement was never resolved — it also failed to record anything, its level
tracking its own capture gain rather than the signal.

## But the ADC data arrives mangled

| rate | nonzero samples | rms | dominant | energy at 1 kHz |
|---|---|---|---|---|
| 48 kHz | 38.2% | -20.1 dBFS | 654.8 Hz | 0.85% |
| 96 kHz | 29.3% | -20.3 dBFS | 581.5 Hz | 0.89% |
| 24 kHz | 38.8% | -18.6 dBFS | 913.1 Hz | 9.78% |
| 8 kHz | 27.1% | -19.8 dBFS | 748.0 Hz | 2.47% |

**60-70% of samples are exactly zero** and the spectrum peaks well away from 1 kHz at every rate. A
continuous sine cannot produce that. Changing the serial rate does not help, so it is not the output
ASRC's conversion ratio.

Meanwhile `Serial Input -> Serial Output` through the same serial port, slots and mux is **bit-exact**
(verified sample by sample against the transmitted values). So the corruption is confined to
**ADC -> decimator -> output ASRC**, and every documented enable in that path is verified set live
during the stream.

## Recommendation

**Drive the board from SigmaStudio over the USBi on a Windows PC and capture with ADI's own
configuration.** That removes my register sequence *and* the mainline Linux driver from the question
in one step — the only two things that have never been independently checked. If the ADC data is
clean under SigmaStudio, diff its register map against `/sys/kernel/debug/regmap/1-003c/registers`
and the difference is the answer. If it is equally mangled, the finding belongs with ADI.

Everything needed for that is in place: the USBi is proven to work (it answered its vendor protocol),
and the register dump path from Linux is a one-liner.

# CORRECTION: left_j broke playback, and it voids the analog-loopback results

`[measured]` 2026-09-17, by ear.

Sequence of events that matters:

1. Framing changed to 64 fs plain I2S (Peter's call). Digital loopback became **bit-exact**.
2. I then changed `dai-format` to **`left_j`**, chasing what I thought was residual bit corruption.
   Digital loopback "did not improve", so I left it in place and carried on.
3. Every analog-loopback measurement (J23 -> J18) was taken **after** that change.
4. Peter listened: **the codec's output was huge noise**, while the identical file on the USB dongle
   was clean tones. Reverted to `i2s`; output is clean tones again.

**A digital loopback is structurally incapable of catching a justification error.** The codec passes
the bits through, so a consistent mismatch cancels end to end and the capture looks perfect. Only the
analog output reveals it, and only ears or an analog instrument can see that.

## What this voids

Everything measured through the analog loopback while `left_j` was live:

- the "0.7x pitch shift" across 250/500/1000/2000 Hz
- "60-70% of samples are exactly zero"
- the conclusion that the **output ASRC** is starving or mis-rated
- the sample-rate sweep that appeared to rule out the ASRC ratio

The source feeding AIN0 during all of those was noise, not a tone, so none of them measured what I
claimed. The ASRC theory is withdrawn - not disproved, just unevidenced.

## What still stands

- The ADC **converts**: silence in gave exact zeros, signal in gave nonzero output. That test's logic
  holds regardless of what the signal was.
- The digital link is **bit-exact** at 64 fs with `i2s` (verified sample by sample).
- Playback is **clean by ear** with `i2s` at 64 fs.
- The residual 0.2% mains-synchronous corruption was measured under `i2s` at 64 fs and stands.

## The rule this session keeps teaching

Three times today a negative result came from an instrument that could not have produced a positive
one: mute-toggling to test an audio path, a USB dongle that was not recording the signal, and now a
digital loopback used to validate an analog-only fault. **After any framing or format change, listen
to the DAC before trusting anything digital built on top of it.**

## Next

Re-patch J23 -> J18 and redo the analog loopback now that playback is verified clean. That is the
test that tells us whether the ADC data path is genuinely faulty or whether it, too, was only ever
reflecting a broken source.

# The capture was listening to the Pi's own transmit (crosstalk), 2026-09-17

`[measured]` The decisive control: **J23 -> J18 physically disconnected**, so no analog path exists.

| condition | capture |
|---|---|
| no playback | exact zeros |
| playback: digital silence | exact zeros |
| **playback: 1 kHz** | **-22.9 dBFS of garbage** |

Garbage appears whenever the Pi **transmits a tone**, with the analog loop unplugged. GPIO21 (SDO)
and GPIO20 (SDI) are adjacent on the header; when the codec's data line is quiet, the coupled
transmit data is what the Pi reads back.

## What this invalidates

**Every capture taken while playback was running** - which is most of the analog work today:

- "silence in -> zeros, tone in -> nonzero, therefore the ADC converts". **Withdrawn.** The
  difference was crosstalk correlating with playback, not the ADC responding to sound.
- the "0.5x pitch shift" and its frequency sweep
- "60-70% of samples are exactly zero"
- the whole J23 -> J18 analog loopback series
- `[suspect]` the 0.2% "mains-synchronous" corruption in the digital loopback was also measured
  during duplex. It may be this same crosstalk rather than EMI, and needs re-measuring capture-only
  before that conclusion is trusted.

It also explains the property that kept recurring and that I kept failing to act on: **the captured
level never responded to DAC volume or PGA gain.** Crosstalk does not care about analog gain. That
signature was visible in the very first analog-loopback sweep and I noted it three times without
drawing the conclusion.

## The clean measurement, at last

Dongle headphone output -> J18, **codec playing nothing** (no transmit, so no crosstalk):

| input | capture |
|---|---|
| silence (control) | exact zeros |
| 500 Hz | **exact zeros** |
| 1000 Hz | **exact zeros** |
| 2000 Hz | **exact zeros** |

So, measured without crosstalk and with the framing fixed: **the ADC path emits exact zeros for any
analog input.** That is a clean statement at last, but it is the same statement as this morning.

## The one thing still never verified

**Nobody has ever confirmed that a signal physically reaches AIN0.** Every ADC test has depended on
either an open-ended cable, or a USB dongle whose two jacks were never identified, or the codec's own
DAC through a cable that turned out to be carrying nothing measurable. Given how many times "no
signal at the input" has turned out to be the answer today, this must be settled with a meter before
anyone concludes the ADC is faulty:

1. **AC volts across J18's two pins while the dongle plays** - expect a few hundred mV. Zero means
   the jack or cable is wrong, again.
2. **DC volts on AIN0 (codec pin 9)** - expect roughly AVDD/2, about 1.65 V. That confirms the input
   is biased and the front end is alive.

Until those two numbers exist, "the ADC is faulty" is not a supportable claim.

# Where this stands at the end of 2026-09-17

## The codec's data line is idle

`[measured]` Capture only, Pi transmitting nothing (so crosstalk is impossible), external source on
the input, codec in TDM4 with the Pi in stereo:

- capture: **exact zeros on both channels**
- **GPIO20 (`ADC_SDATA0` from the codec): low on 40 of 40 samples**

An all-zero I2S stream also holds the line low, so this is consistent rather than conclusive on its
own — but combined with the capture it says the codec is driving nothing but zeros out of its ADC
data pin, while demonstrably generating BCLK and LRCLK on the same header.

## The codec-TDM4 / Pi-stereo experiment is UNRESOLVED, not failed

Peter's model - a stereo receiver taking the first 32-bit word of each half-frame, so a 128-BCLK
codec frame lands slots 0 and 2 - is sound, and it is what `DATA_OVER_I2S.md` measured on the
ADAU1860. It could not be **tested** here: identifying slots needs a signal source, the only
available source is the Pi's own transmitter, and the moment it transmits, SDO->SDI crosstalk swamps
the result. Proof it was crosstalk: moving the signals to slots 1 and 3, which should have silenced
the capture entirely, changed nothing at all.

**It can be tested the moment the ADC produces samples** - the ADC is the one crosstalk-free source.
The overlay has been reverted to plain stereo I2S (the configuration with the bit-exact loopback) so
the rig sits in its best-known state; re-applying the experiment is four lines in the codec subnode.

## Everything verified working

codec at 0x3C; 12.288 MHz crystal (measured, and confirmed by UG-807); control port; codec generating
clocks the Pi locks to; mainline driver built out-of-tree and autoloading, card + 50 ALSA controls;
J8/J10/J12/J17 fitted, J15 clear; DAC audible and clean with `i2s` framing; **digital link bit-exact
through the codec** at 64 fs; registers verified live mid-stream.

## The single open fault

**The ADC section emits digital zero**, on both channels, symmetrically, for every input and setting
tried: AIN0 and AIN1, PGA off / 0 / +18 / +35 dB, line and PGA modes, 250 Hz to 4 kHz, at 8/24/48/96
kHz, sourced from a USB dongle and from the codec's own DAC, measured with and without crosstalk.

## What has never been measured, and must be before blaming the codec

1. **AC volts across the input jack's pins while a source plays.** Every ADC test today assumed a
   signal was arriving. "Nothing was connected" has already been the answer twice.
2. **DC volts on the AIN pin** (pin 9 = AIN0, pin 14 = AIN1): expect ~AVDD/2, about 1.65 V.

With those two numbers, the conclusion is forced either way. Without them it is a guess.

## Then: SigmaStudio over the USBi

If the input signal and bias are both confirmed good and the ADC still emits zeros, configure the
board from SigmaStudio on a Windows PC and capture with ADI's own register set. That removes this
session's configuration **and** the Linux driver from the question. Diff its register map against
`/sys/kernel/debug/regmap/1-003c/registers`; if it is equally silent, the finding belongs with ADI.

## Consequence for the four-channel plan

`ADC_SDATA1` is not wired, and RP1 wants a 64 fs frame, which is 2 slots. **One lane at 64 fs carries
two channels, not four.** Mic + X/Y/Z therefore needs either the codec-TDM4 / Pi-stereo arrangement
above (2 of 4 slots, freely choosable via the SOUT muxes), or `ADC_SDATA1` wired as a second lane -
which additionally needs a one-line driver patch, because mainline claims that pin for CLKOUT
(`MODE_MP6 = 0x12` at probe). `CONFIG-PLAN.md` still assumes four channels on one lane and needs
revising.
