# ArduPlane native on BB1: first bring-up, 2026-11-18

Peter asked: *"are we running ardupilot plane natively on bb1 yet?"*. The answer was no, and then
*"Yes, bring it up"*.

**Result: ArduPlane runs natively on BB1's CM5.** The IMU and baro are healthy, it streams MAVLink,
and it restarts cleanly once `patches/0003` is applied. **EKF3 is not yet producing data**: a plane
needs a GPS 3D fix to start it, and the GPS is not connected to ArduPilot yet.

## The board

`[measured]` `Raspberry Pi Compute Module 5 Rev 1.0`, hostname `bb1`, machine-id
`ad0a0fbd3b064476a100b652968a1ed0`, Debian 13 trixie, kernel `6.18.50+rpt-rpi-2712`, 4 cores, 4 GiB.
It is on a direct cable to the Mac and reached at `node@fdbf:e1d0:e7be:74bc:57ab:fcc9:dc7b:e2e6`
(IPv6 ULA). **BB1 has no internet**, so the source and wheels were staged on the Mac and copied over.
Its clock is about 84 days slow. Boot config was **not** changed: BB1 already had `spi0-1cs`,
`spi3-1cs`, `uart0-pi5` and I2C on.

## Three findings

**1. The BMP581 driver cannot be started twice without a power cycle. Fixed by `patches/0003`.**
Run 2 of the day reported `Config Error: Baro: unable to initialise driver` every 5 s and stuck in
`INITIALISING` with every sensor reading 0, **while still sending heartbeats**. The bus was fine:
CHIP_ID read 0x50 200/200, and the scan showed 0x2d 0x34 0x46 0x48 0x6b 0x77.
`AP_Baro_BMP581::init()` requires `INT_STATUS.por` (0x27 bit 4) and `STATUS.nvm_rdy`, but never resets
the chip, and `INT_STATUS` is clear-on-read (`scripts/bmp581_por.py`):

```
after one ArduPlane run:   INT_STATUS 0x00   STATUS 0x01
CMD 0x7E <- 0xB6, 5 ms:    INT_STATUS 0x10   STATUS 0x02   CHIP_ID 0x50
read again:                INT_STATUS 0x00   (clear-on-read confirmed)
```

The controls were run back to back, with no power cycle:

| Run | Binary | Config errors | Baro |
|---|---|---|---|
| A | patched | 0 | healthy, 1019.37 hPa |
| N | **unpatched** (straight after A) | **12** | absent, all sensors 0 |
| B | patched (straight after N) | 0 | healthy, 1019.31 hPa |

Under `Restart=on-failure`, any crash or restart of the service would have left the board without
a baro. **File 0003 upstream along with 0001/0002.**

**2. Plane's default airspeed driver claimed the barometer.** `MS4525[0]: Found bus 1 addr 0x46`:
`MS4525D0_I2C_ADDR3` is 0x46, the BMP581's address. The hwdef now defaults `ARSPD_TYPE` to 0. Run C
confirmed `ARSPD_TYPE = 0` and `No airspeed sensor`, with the baro still healthy.

**3. EKF3 will not start without GPS on a plane.** `AP_NavEKF3_core.cpp:457`: "If we are a plane
and don't have GPS lock then don't initialise" → `EKF3 init failure: No GPS lock`. On the bench AHRS
runs DCM. **Without the DAN-F10N connected and a sky view, there will be no EKF data.**

## GPS connected (Peter: "Yes, connect GPS"), the same day

**Before ArduPilot** (`scripts/gnss_sniff.py`, read-only): the DAN-F10N on `/dev/ttyAMA0` was sending
NMEA at **38400** baud with a 3D fix: 8 SVs used (GPS 2 + Galileo 6), HDOP 1.37, C/N0 22–29 dB-Hz.
Nothing else had the port open. The position is not recorded in this repo, on purpose.

**ArduPlane `--serial3 /dev/ttyAMA0`:** `GPS 1: detected u-blox` at 9.8 s → `u-blox configured` →
fix 3D with 5–6 SVs → **`EKF3 IMU0 initialised` at 10.8 s, `tilt alignment complete` at 12.7 s**.
EKF flags `0x00a7` = attitude, vel horiz, vel vert, pos_vert_abs, **const_pos_mode**. Home position set.
It stays in const_pos_mode on the bench: with no working compass, a plane aligns yaw from GPS
velocity, which needs it moving. **So roll/pitch, velocity and altitude are EKF output; horizontal
position and yaw are not yet.**

**The receiver is now reconfigured, persistently.** `GPS_AUTO_CONFIG=1`, `GPS_SAVE_CFG=2` (saves to
the receiver's flash). Afterwards it speaks **UBX only at 230400 baud**: NAV-PVT/POSECEF/TIMEGPS +
MON-RF, no NMEA. Anything else that expects NMEA at 38400 on that port will see nothing. Factory reset
is UBX-CFG-CFG (clear + load). That is not done here.

**Satellite count dropped from 8 to 5 after reconfiguration, then recovered to 7** (`scripts/ubx_pvt.py`,
the receiver's own NAV-PVT, not ArduPilot's view): 5 SVs, hAcc 25–30 m, pDOP 11–12 for 3 minutes,
then 7 SVs, hAcc 10.5 m, pDOP 2.9. NAV-SAT: best C/N0 **22 dB-Hz** (open sky is 35–45), with 2 GPS +
3 GAL used. MON-RF: `jammingState 0`, `jamInd 12`. **Verdict: weak sky view plus a restart after the
signal-config change, not jamming and not a broken config.** For a real EKF test, BB1 needs a proper
sky view.

**Bridge end to end** (`aerosync/ekf_bridge.py` on a second MAVLink output, `--serial1
udp:127.0.0.1:14552`): `aerosync.ekf/1` frames at the requested rate, attitude 10–20 ms old. After
ArduPlane stopped, every field went `stale` and `valid: false`: the staleness guard fired live.

**Bridge bug found and fixed:** in const_pos_mode the bridge still emitted `GLOBAL_POSITION_INT`
lat/lon and `LOCAL_POSITION_NED` x/y, even though the EKF said `pos_horiz_abs: false`. That is a
position the EKF disowns. Those fields are now `null` with named faults (`position.horizontal`,
`local_ned.horizontal`) unless the EKF reports a horizontal solution and is not in const_pos_mode.
Tests 16 → 21: the 3 new POSITIVE checks **fail against the old bridge** and pass with the fix.
Live on BB1: 62 frames, **0 with a numeric latitude**, attitude still flowing.

## Feeding the aeronode collector (Peter: "Yes, feed collector"), the same day

**Service installed and running, NOT enabled at boot.** `service/arduplane.service` was rewritten:
`--serial0 udp:192.168.144.1:14550` (the collector, the same target the old Pixhawk 6X used, so the
collector needed no change), `--serial1 udp:127.0.0.1:14552` (ekf_bridge), `--serial3 /dev/ttyAMA0`
(GPS), `WorkingDirectory`/`StateDirectory=/var/lib/ardupilot`, `Restart=on-failure` (safe now because
of 0003). `/usr/local/bin/arduplane` has the same sha256 as the build (`231c6321…`).
`systemd-analyze verify` is clean, and `systemctl is-enabled` reports `disabled`.

**The collector connected on its next 60 s retry** and fetched 945/945 parameters. 29/29
SET_MESSAGE_INTERVAL were acked.

**Then the high-rate streams ran at 1 Hz.** ArduPilot DENIES any interval request faster than the
loop allows (`GCS_Common.cpp:3256`, "Requested rate ... too fast. Increase SCHED_LOOP_RATE"; the cap
is `interval_ms × 800 < loop_period_us`, `:278`). Plane's default loop is 50 Hz, so anything above
40 Hz is refused, and the collector asks for 50–100 Hz. Its own config says the fleet's 6X runs
**`SCHED_LOOP_RATE = 400`** ("loop 400 confirmed live"). Set to 400 with `scripts/param_set.py`
over the local port (read back 50 → 400), then the service was restarted.
- **Result:** every stream at target. attitude, attitude_q, imu, global_position and vfr_hud at
  100 Hz; baro, ekf_status, ahrs2 and vibration at 50 Hz; the rest at 10 Hz. ArduPilot's scheduler
  load is **1.1 %**, and the process uses 6.5–10 % of one core.
- **Dead streams, all expected:** imu2, imu3, baro2, gps2_raw (single sensors), battery (no
  monitor), mcu (not on Linux), gps_origin (no EKF origin while in const_pos_mode).
- **This default cannot live in the hwdef.** `AP_Scheduler.cpp:43-47` picks 50 for Plane with no
  `#ifndef`. It is a parameter in `/var/lib/ardupilot/ArduPlane.stg`, and **a fresh state directory
  falls back to 50**, which brings the 1 Hz streams back. Re-apply it after any wipe.

**At the point of use (MQTT):** the collector boots IDLE (`record_on_start = false`). It publishes
live and persists nothing until a recording starts, and starting one **auto-arms** the FC
(`auto_arm_on_record`). No recording was started. In 10 s of `mosquitto_sub`:
`aeronode/BB1/{attitude,attitude_q,imu,global_position,vfr_hud}` 1001 each, and
`{ekf_status,baro,ahrs2,vibration}` 501 each, alongside the collector's own env/spl/lite topics.

**BB1's clock is wrong in every published timestamp** (`"ts":"2026-08-26…"`, about 84 days slow,
no time sync offline). The collector has `require_gps_for_record = true` for starting a recording.
Whether it corrects the system clock from GPS was not checked. **Anything that trusts `ts` today is
wrong.**

## Enabled at boot and proven by a reboot (Peter: "Yes, enable at boot"), the same day

`systemctl enable arduplane` created the `multi-user.target.wants` symlink. **Proof is a reboot,
not the symlink:** the boot_id changed and BB1 was back on the network after about 15 s.
- `arduplane` active **7.5 s into boot**, `NRestarts=0`. Parameters survived:
  `SCHED_LOOP_RATE = 400`, `ARSPD_TYPE = 0`.
- **BMP581 healthy after a reboot that did not power-cycle it.** That is patch 0003 working in the
  real boot path. gyro/accel/baro present+enabled+healthy, 1018.32 hPa, scheduler load 1.0 %.
- Collector reconnected by itself: attitude/imu/global_position/vfr_hud at 99.9–100.1 Hz,
  baro/ekf_status at 49.9 Hz. MQTT in 10 s: 1000 per 100 Hz topic, 501 per 50 Hz topic.
- `aeronode-wifi-net-mode.service` is `failed`. It was already failed **before** this work and
  has nothing to do with ArduPlane. Not touched.
- The system clock reset again on reboot (about 13:08, the same wrong date). See "Clock" below.

**The GPS came back COLD.** For 9+ minutes after boot: fix_type 1, 0 SVs, `PreArm: GPS 1: Bad
fix` every 31 s, so **EKF3 stays uninitialized** (`0x0400`) and the 100 Hz attitude on MQTT is DCM,
not EKF. I stopped ArduPlane for about 20 s to read the receiver itself: **1 SV tracked at C/N0 32
dB-Hz** (so the antenna and RF path work; `jammingState 0`), NAV-PVT `hAcc 4294967.3 m`, the "no
knowledge" value. The receiver lost time, position and almanac across the reboot and is doing a
full cold start, which at this indoor sky view is slow. Before the reboot it had been tracking for
hours.

### Root cause: V_BCKP is not connected, and the GNSS rail cycles on reboot (Peter: "check the schematic for V_BCKP")

**Schematic** `[repo: ~/Downloads/Schematic for Aeronode HW ver 0.0.2 rev 1.PDF, sheet 9 (GNSS) +
sheet 3 (CM5), rendered and read]`:
- **DAN-F10N pin 55 `V_back` = `nc`**, with a red no-connect cross and the note "leave open if not
  used for backup". No coin cell, no supercap, no always-on feed. **The receiver has no backup domain.**
- `Vgps` (pins 52/53) comes from **U11 TPS7A2033** (3.3 V LDO, Vin = `Vcm5`). Its `En` is `GPS_Power`,
  pulled up by **R37 100k** to `Vcm5`. The designer's notes on it: "reg has internal 500k pulldown -
  so this value might need to be smaller", "CPU must pull low only when GPS should be switched off /
  cold started", and a large red **"?"**.
- Sheet 3: `GPS_Power` = CM5 pin 82 = **GPIO38 (`SDA0`)**, "1k8 pullup to 3.3V" on the CM5.
  `GPS_AntSel` = pin 97 = GPIO34. `GPS_nRes` = pin 100 = GPIO35 (15k pull-up).
  `GPS_TimePulse` = pin 111 = GPIO42.

**Measured on BB1:**
- **The GNSS power-cycles with a reboot.** UBX-NAV-STATUS `msss` (time since the receiver's own
  start) = **1143.1 s** against Linux uptime **1142.0 s** (`scripts/ubx_uptime.py`). An ArduPlane
  *service* restart does not do this: after the SCHED_LOOP_RATE restart it had a fix again at once.
- `pinctrl`: GPIO38 `no pd | hi` (no function, internal pull-down, held high by the 1k8), so Linux
  is not switching it off. The drop has to be on the supply side during the CM5 reset (the 3.3 V
  feeding the 1k8 pull-up, or `Vcm5` into U11). Which one is CANNOT-MEASURE-FROM-A-DESK: scope
  **TP15 `Vgps`** across a `reboot`.
- GPIO34 `GPS_AntSel` = **output low = internal antenna** (sheet: "L = int ant"; datasheet:
  "Low on the pin selects the internal antenna (default)"). That fits the weak 22–32 dB-Hz signals.

**Datasheet** `[fetched: u-blox DAN-F10N Data sheet UBXDOC-963802114-13074 R04, 2025-06-27]`:
V_BCKP is the "Backup voltage supply", 1.65–3.6 V, **31 µA** in hardware backup mode (VCC = 0) and
about 3 µA in normal operation. Table 2: TTFF **cold 28 s vs hot 2 s**. Sensitivity needed:
**cold start −145 dBm, hot start −156 dBm, tracking −164 dBm**. A cold start needs 11 dB more signal
than a hot start. Before the reboot the receiver was tracking. After the reboot it lost everything
(no V_BCKP) and had to acquire cold.

> **`[correction]`, the same day.** I first wrote that it "cannot acquire" indoors. That is too
> strong. **The previous boot was also a cold start** (same circuit), and it had reached a fix with
> 8 SVs and HDOP 1.37 on the onboard antenna by the time of the first sniff (Peter: "we should get fix
> with onboard antenna"). So a cold start here is slow or uncertain, not impossible: still no fix
> 25 min after this boot. **A second candidate is not yet separated:** the earlier cold start used the
> receiver's factory config, and this one uses ArduPilot's (saved to flash: UBX @ 230400, GNSS
> GPS+SBAS+GAL+BDS, QZSS off, its own signal set). The missing V_BCKP is still real, and it still
> turns every reboot into a cold start.

**Fix options, for Peter and the board owner:**
1. **Next board rev: feed V_BCKP from an always-on source** (e.g. a small LDO or diode from the
   2S-pack-backed VSYS, or a supercap/ML cell). 31 µA is negligible. This turns every reboot into a
   ~2 s hot start.
2. **Rev 0.0.2 bench rework:** the same thing by hand on pin 55.
3. **Find out whether the rail cycling on reset is intended.** The designer's own notes say
   `GPS_Power` should only go low when the CPU *wants* a cold start.
4. **Use the external antenna** (`GPS_AntSel` high + an antenna on J13 u.FL), or put BB1 under
   open sky. This does not fix the reboot, but it lets a cold start finish.

## Still open

- **GNSS cold start on every boot**: no V_BCKP plus a rail that cycles on reset (above). Also an
  internal antenna indoors.
- **Clock:** BB1 needs a time source (GPS → chrony, or NTP when online) before any recording is
  trusted.
- **Sky view** for the GPS, then a moving test (or a working compass) so EKF3 aligns yaw and leaves
  const_pos_mode. Yaw is drifting freely meanwhile (e.g. 256°), and it is published at 100 Hz.
- **Attitude reads about 0–11° roll and 2–7° pitch at rest.** Either the board is not sitting
  level or `ROTATION_NONE` / the accel offsets are wrong. CANNOT-MEASURE-FROM-A-DESK: check how BB1
  is sitting, then run an accel calibration.
- The `clone`/`prereqs` steps of `build-on-board.sh` assume internet access, which BB1 does not have.
