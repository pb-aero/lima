# ArduPlane native on BB1: first bring-up, 2026-11-18

Peter asked: *"are we running ardupilot plane natively on bb1 yet?"*. The answer was no, and then
*"Yes, bring it up"*.

**Result: ArduPlane runs natively on BB1's CM5.** The IMU and baro are healthy, it streams MAVLink,
and it restarts cleanly once `patches/0003` is applied. **EKF3 is not yet producing data**: a plane
needs a GPS 3D fix to start it, and the GPS is not connected to ArduPilot yet.

## The board

`[measured]` `Raspberry Pi Compute Module 5 Rev 1.0`, hostname `bb1`, machine-id
`ad0a0fbd3b064476a100b652968a1ed0`, Debian 13 trixie, kernel `6.18.50+rpt-rpi-2712`, 4 cores, 4 GiB.
It is on a direct cable to the Mac and reached at `node@fdbf:e1d0:e7be:74bc:57ab:fcc9:dc7b:e2e6`
(IPv6 ULA). **BB1 has no internet**, so the source and wheels were staged on the Mac and copied over.
Its clock is about 84 days slow. Boot config was **not** changed: BB1 already had `spi0-1cs`,
`spi3-1cs`, `uart0-pi5` and I2C on.

## Three findings

**1. The BMP581 driver cannot be started twice without a power cycle. Fixed by `patches/0003`.**
Run 2 of the day reported `Config Error: Baro: unable to initialise driver` every 5 s and stuck in
`INITIALISING` with every sensor reading 0, **while still sending heartbeats**. The bus was fine:
CHIP_ID read 0x50 200/200, and the scan showed 0x2d 0x34 0x46 0x48 0x6b 0x77.
`AP_Baro_BMP581::init()` requires `INT_STATUS.por` (0x27 bit 4) and `STATUS.nvm_rdy`, but never resets
the chip, and `INT_STATUS` is clear-on-read (`scripts/bmp581_por.py`):

```
after one ArduPlane run:   INT_STATUS 0x00   STATUS 0x01
CMD 0x7E <- 0xB6, 5 ms:    INT_STATUS 0x10   STATUS 0x02   CHIP_ID 0x50
read again:                INT_STATUS 0x00   (clear-on-read confirmed)
```

The controls were run back to back, with no power cycle:

| Run | Binary | Config errors | Baro |
|---|---|---|---|
| A | patched | 0 | healthy, 1019.37 hPa |
| N | **unpatched** (straight after A) | **12** | absent, all sensors 0 |
| B | patched (straight after N) | 0 | healthy, 1019.31 hPa |

Under `Restart=on-failure`, any crash or restart of the service would have left the board without
a baro. **File 0003 upstream along with 0001/0002.**

**2. Plane's default airspeed driver claimed the barometer.** `MS4525[0]: Found bus 1 addr 0x46`:
`MS4525D0_I2C_ADDR3` is 0x46, the BMP581's address. The hwdef now defaults `ARSPD_TYPE` to 0. Run C
confirmed `ARSPD_TYPE = 0` and `No airspeed sensor`, with the baro still healthy.

**3. EKF3 will not start without GPS on a plane.** `AP_NavEKF3_core.cpp:457`: "If we are a plane
and don't have GPS lock then don't initialise" → `EKF3 init failure: No GPS lock`. On the bench AHRS
runs DCM. **Without the DAN-F10N connected and a sky view, there will be no EKF data.**

## GPS connected (Peter: "Yes, connect GPS"), the same day

**Before ArduPilot** (`scripts/gnss_sniff.py`, read-only): the DAN-F10N on `/dev/ttyAMA0` was sending
NMEA at **38400** baud with a 3D fix: 8 SVs used (GPS 2 + Galileo 6), HDOP 1.37, C/N0 22–29 dB-Hz.
Nothing else had the port open. The position is not recorded in this repo, on purpose.

**ArduPlane `--serial3 /dev/ttyAMA0`:** `GPS 1: detected u-blox` at 9.8 s → `u-blox configured` →
fix 3D with 5–6 SVs → **`EKF3 IMU0 initialised` at 10.8 s, `tilt alignment complete` at 12.7 s**.
EKF flags `0x00a7` = attitude, vel horiz, vel vert, pos_vert_abs, **const_pos_mode**. Home position set.
It stays in const_pos_mode on the bench: with no working compass, a plane aligns yaw from GPS
velocity, which needs it moving. **So roll/pitch, velocity and altitude are EKF output; horizontal
position and yaw are not yet.**

**The receiver is now reconfigured, persistently.** `GPS_AUTO_CONFIG=1`, `GPS_SAVE_CFG=2` (saves to
the receiver's flash). Afterwards it speaks **UBX only at 230400 baud**: NAV-PVT/POSECEF/TIMEGPS +
MON-RF, no NMEA. Anything else that expects NMEA at 38400 on that port will see nothing. Factory reset
is UBX-CFG-CFG (clear + load). That is not done here.

**Satellite count dropped from 8 to 5 after reconfiguration, then recovered to 7** (`scripts/ubx_pvt.py`,
the receiver's own NAV-PVT, not ArduPilot's view): 5 SVs, hAcc 25–30 m, pDOP 11–12 for 3 minutes,
then 7 SVs, hAcc 10.5 m, pDOP 2.9. NAV-SAT: best C/N0 **22 dB-Hz** (open sky is 35–45), with 2 GPS +
3 GAL used. MON-RF: `jammingState 0`, `jamInd 12`. **Verdict: weak sky view plus a restart after the
signal-config change, not jamming and not a broken config.** For a real EKF test, BB1 needs a proper
sky view.

**Bridge end to end** (`aerosync/ekf_bridge.py` on a second MAVLink output, `--serial1
udp:127.0.0.1:14552`): `aerosync.ekf/1` frames at the requested rate, attitude 10–20 ms old. After
ArduPlane stopped, every field went `stale` and `valid: false`: the staleness guard fired live.

**Bridge bug found and fixed:** in const_pos_mode the bridge still emitted `GLOBAL_POSITION_INT`
lat/lon and `LOCAL_POSITION_NED` x/y, even though the EKF said `pos_horiz_abs: false`. That is a
position the EKF disowns. Those fields are now `null` with named faults (`position.horizontal`,
`local_ned.horizontal`) unless the EKF reports a horizontal solution and is not in const_pos_mode.
Tests 16 → 21: the 3 new POSITIVE checks **fail against the old bridge** and pass with the fix.
Live on BB1: 62 frames, **0 with a numeric latitude**, attitude still flowing.

## Still open

- **Sky view** for the GPS, then a moving test (or a working compass) so EKF3 aligns yaw and leaves
  const_pos_mode.
- **Attitude reads about 8–11° roll and 3–7° pitch at rest** (DCM, accel uncalibrated). Either the
  board is not sitting level or `ROTATION_NONE` / the accel offsets are wrong. CANNOT-MEASURE-FROM-
  A-DESK: check how BB1 is sitting, then run an accel calibration.
- **Feeding the collector.** It listens on `udpin:192.168.144.1:14550` and logs "FC connect failed"
  every 60 s. Its config allows calibration and arm commands, and it writes `flights.db`, so
  pointing ArduPlane at it is Peter's call.
- **Service.** `service/arduplane.service` still uses the deprecated `-A`/`-B` flags and has no
  `WorkingDirectory`. ArduPilot writes `ArduPlane.stg` into the cwd (it landed in `~node`).
- The `clone`/`prereqs` steps of `build-on-board.sh` assume internet access, which BB1 does not have.
