## It runs, and it cannot arm — as designed `[measured]`

Startup emits, among the MAVLink stream:

```
Config Error: Baro: unable to initialise driver
Config Error: fix problem then reboot
```

That is `--board=linux`'s `HAL_INS_DEFAULT HAL_INS_NONE` doing exactly what §2 of `NOTES.md` said
it would: no IMU, no baro, no compass declared. The binary is a working MAVLink-speaking
ArduPlane that will refuse to arm. For a bare Pi 5 with no autopilot HAT this is the correct and
only outcome — it is not a fault to chase.

Note also: with no `--serial0` argument the MAVLink stream goes to **stdout**, which is why
running it bare fills the terminal with binary. Real use wants e.g.
`./build/linux/bin/arduplane --serial0 udp:<gcs-ip>:14550`. Full option list from `--help`
includes `--serial0..9`, `tcp:`/`udp:`/`udpin:` endpoints, `--log-directory`,
`--storage-directory`, `--cpu-affinity`.

## Prediction 1b confirmed at the point of use `[measured]`

`NOTES.md` §1b predicted from source that `--board=linux` compiles `Empty::GPIO`, never calls the
Pi-5 detector, and therefore never prints `RPI 5`. Checked against the generated config:

```
GPIO_RPI compiled in : no
  -> Empty::GPIO. No /dev/mem mapping, no pin claims, no Pi-5 detector call.
```

and the startup output contains no `RPI 5` and no `Cannot detect board-type`. Both absences are
correct. **The `strncmp(entry->d_name, "soc", 4)` bug in `Util_RPI.cpp:62` is real and still
unfixed upstream, but this build cannot reach it.** It remains a live hazard for `navio2` /
`pilotpi` / `navigator64` on this kernel, where it becomes an `AP_HAL::panic` at startup.

## The ADAU1860 pins are untouched — and the first measurement that said otherwise was mine

`verify` samples `pinctrl get 18-21` either side of the run. It showed GPIO19 reading `lo` before
and `hi` after, which looks like ArduPilot claiming an ADAU1860 pin.

**It is not.** Negative control — six samples with no `arduplane` process running at all:

```
sample 1: 18:lo 19:lo 20:lo 21:lo
...
sample 6: 18:lo 19:hi 20:lo 21:lo      <- flips on its own
```

GPIO19 is `I2S1_WS`, a live frame clock. `pinctrl`'s level column is an instantaneous sample of a
signal that is moving, so it varies run to run regardless of ArduPilot. The columns that would
actually prove a claim — the **mux** (`a4 // I2S1_WS`) and the **pull** (`pn`) — are byte-identical
before, during and after. Combined with `Empty::GPIO` being the compiled backend, ArduPilot has no
code path that could touch these pins.

Instrument note: my first attempt at this control printed `18:=| 19:=| ...` because I read
`pinctrl`'s `$4` (the literal `|`) instead of `$5`. A control that returns punctuation is not a
result — it is a broken instrument, and it would have been easy to read the null output as "no
change" and move on.

## The side effect: a kernel arrived that nobody asked for `[measured]`

`apt` history, traced to a single command:

```
Commandline: apt-get --assume-yes install build-essential ccache g++ gawk git make wget valgrind
             screen python3-pexpect astyle python3-dev libpython3-stdlib libtool-bin ppp
             g++-arm-linux-gnueabihf
Install: ... linux-image-6.18.39+rpt-rpi-2712 (automatic)
             linux-image-6.18.39+rpt-rpi-v8   (automatic)
             linux-headers-* / linux-kbuild-6.18.39+rpt (automatic)
```

**`g++-arm-linux-gnueabihf` is the culprit** — the 32-bit ARM cross-compiler drags
`linux-libc-dev-armhf-cross` -> `linux-headers-rpi-*` -> `linux-image-rpi-*`, and those
meta-packages pull the current Raspberry Pi kernel, 6.18.39. Both `/boot/firmware/kernel_2712.img`
and `kernel8.img` were rewritten at 17:05.

The irony: **that cross-compiler is useless to this build.** `hwdef/linux` sets `TOOLCHAIN native`;
we compile aarch64 on the Pi. `install-prereqs-ubuntu.sh` installs it unconditionally because most
of ArduPilot's Linux boards are 32-bit cross targets. My `install_ardupilot.sh` skipped the SITL
graphics stack but did not anticipate this, which is a defect in my kit.

State right now:

- **Running kernel is unchanged:** `uname -r` = `6.12.47+rpt-rpi-2712`. Nothing has broken.
- **Next reboot boots `6.18.39+rpt-rpi-2712`.**

**Peter's ruling, 2026-09-04: accept 6.18.39.** No rollback performed.

`[gap]` **Consequence to carry forward:** every ADAU1860 / RP1 I2S result in
`linux/adau1860-pi5/` was measured on `6.12.47+rpt-rpi-2712`. After the next reboot they are
claims about a kernel the machine is no longer running — device-tree node names, `dwc-i2s`
behaviour and overlay compatibility all sit on that version. Re-verify the 4-lane duplex bring-up
on 6.18.39 before trusting it again.

# Part 2 — the Pi as flight controller (2026-09-04, later)

Peter connected a Pixhawk 6C over USB, wanting its raw IMU over MAVLink as the Pi ArduPilot's
input, then ruled: **he wants the Pi to be the flight controller.**

## Two blockers found before any work started

**1. The Pi cannot see the Pixhawk.** `[measured]` No `/dev/ttyACM*`, empty `/dev/serial/by-id/`,
and the USB tree shows only a keyboard. The decisive detail is that `dmesg` holds **no USB event
at all** — not a failed enumeration, not an over-current trip. That is physical: cable or port,
with a charge-only USB-C cable the usual cause. A watch is running for the device appearing.

**2. ArduPilot has no MAVLink IMU input. There is no code path.** `[measured]`
`AHRS_EHS_TYPE` values are `0:None, 1:VectorNav, 2:MicroStrain5, 5:InertialLabs, 6:Trimble GSOF,
7:MicroStrain7, 8:SBG, 10:Aeron, 11:SensAItion` — every one a vendor binary protocol on a serial
port, none of them MAVLink. `AP_InertialSensor_ExternalAHRS::handle_external()` is fed only by
those backends, and `HIL_SENSOR`/`HIL_STATE` handling is gone from `GCS_MAVLink` entirely.
A Pixhawk streaming `RAW_IMU` cannot become another ArduPilot's INS.

So the Pixhawk is not the route. The Pi needs sensors on its own buses — and it already has them.

## What was actually on the machine `[measured]`

A read-mode scan of both I2C buses (the ADAU1860 sits on i2c-1 and was left alone):

```
i2c-1: 0x67  ADAU1860 codec (Peter's, untouched)
i2c-2: 0x5c  LPS22HB barometer     WHO_AM_I 0xB1
       0x68  MPU-9250 IMU          WHO_AM_I 0x71
```

The MPU-9250 is the one `dsp/vibration-reference/capture_mpu.py` already uses. The LPS22HB was
an unlooked-for find and it is what makes a real sensor stack possible — ArduPilot's
`AP_Baro_LPS2XH` defines `LPS22HB_WHOAMI 0xB1`, matching exactly, and exposes a plain I2C
`probe()`.

## Result — ArduPilot boots as a flight controller `[measured]`

hwdef additions (modelled on `blue`, which runs the same MPU-9250 at `I2C:2:0x68`):

```
undef HAL_INS_DEFAULT                                   # beat HAL_INS_NONE from ../linux
IMU Invensense I2C:2:0x68 ROTATION_NONE
COMPASS AK8963:probe_mpu9250 I2C:2:0x0c ROTATION_NONE
BARO LPS2XH I2C:2:0x5c
```

Startup, in full:

```
RPI 5
AP_Logger_File: buffer size=204800
LPS2XH whoami 0xB1
Init GyroMPU: temp reset IMU[0] 1562 0
Ground start
Beginning INS calibration. Do not move plane
Calibrating barometer
Barometer 1 calibration complete
MS4525[0]: no sensor found
Airspeed 1 init failed
ArduPilot Ready
```

`Config Error: Baro: unable to initialise driver` is **gone**. IMU[0] initialises, the barometer
calibrates, and the vehicle reaches **ArduPilot Ready**. ADAU1860 pins unchanged throughout
(`18-21 a4/pn` before and after).

## It still cannot fly anything, and this is the important part

`[measured]` `HAL_Linux_Class.cpp:240` — with no matching subtype, `pi5` falls through to:

```c
static Empty::RCOutput rcoutDriver;
```

**There is no PWM output.** Not a weak one — an empty stub. The board cannot drive a servo or an
ESC, so "flight controller" is true of the sensor and estimation stack and false of the vehicle
interface. Closing that means an output backend: `RCOutput_PCA9685` over I2C (what PilotPi and
OBAL use), `RCOutput_Sysfs` on a kernel PWM chip, or new RP1 PWM support. None exists for a bare
Pi 5 today.

## Open `[gap]`

1. **No PWM output** (above). The blocker for any actual vehicle.
2. **Compass unconfirmed.** No AK8963 line appeared in the startup output. Not fatal — ArduPilot
   boots without a compass — but the probe is unproven, and `0x0c` did not answer the bus scan
   (expected: it sits behind the MPU's aux bus, only reachable once the MPU enables passthrough).
3. **All three rotations are `ROTATION_NONE` placeholders.** This asserts the sensors are mounted
   level and facing forward. Nobody has checked. Attitude output is meaningless until set.
4. **I2C is the wrong bus for a flight IMU.** `capture_mpu.py`'s own header says polling over I2C
   "jitters by hundreds of microseconds", and the script refuses to run if the bus cannot sustain
   2x the requested rate. ArduPilot uses the MPU's FIFO so it is not fatal — `bebop`, `blue` and
   `disco` ship exactly this — but SPI is the right answer for anything beyond a bench.
5. **Linux is not an RTOS.** No hard real-time guarantee, no independent failsafe watchdog. This
   is a development and analysis platform, not something to put in the air.

# Part 3 — EKF3 as an AHRS

Peter's actual interest: **EKF3 running as their own AHRS.** PWM output is therefore irrelevant;
what matters is whether the estimator initialises and produces attitude.

## Two corrections to Part 2

**The compass works.** `[measured]` `SYS_STATUS` reports `3D_MAG present / enabled / healthy =
True`. Part 2 flagged it unproven because no AK8963 line appeared in the console output — that was
reading *absence of a log line* as *absence of a sensor*, with the console buffering problem from
§7 making the absence meaningless. Gyro, accel, mag and baro are all present, enabled and healthy;
only GPS and airspeed are absent.

**The IMU is mounted upside down.** `[measured]` Two independent paths agree:

| Instrument | Reading | Implies |
|---|---|---|
| MAVLink `RAW_IMU` at rest | `xacc=47 yacc=-264 zacc=+939` mg | gravity along **+Z**; a level, upright board reads about **-1000 mg** |
| Direct register read, `0x3B` | z ≈ **-0.96 g** | chip's own Z negative -> chip top face down |

These look contradictory and are not: `AP_InertialSensor_Invensense.cpp:589` builds the body-frame
vector as `Vector3f(int16_val(data,1), int16_val(data,0), -int16_val(data,2))` — X and Y swapped,
**Z negated**. Chip -0.96 g becomes body +0.96 g. Both paths therefore say *inverted*, and
`ROTATION_ROLL_180` is correct. It is now set on the IMU and the compass.

`[gap]` A residual ~15 deg remains after the 180 deg flip (`yacc = -264 mg` ~ 15.3 deg, matching
180 - 164.6). That is either the board sitting tilted on the bench or a real mounting angle.
**CANNOT-MEASURE-FROM-A-DESK** — it needs eyes on the rig. `ROTATION_ROLL_180` is the right
discrete choice either way.

## Why EKF3 was not running `[measured]`

```
EKF_STATUS_REPORT flags = 0x0400 -> GPS_GLITCHING     (no ATTITUDE bit)
SYS_STATUS AHRS: present=True enabled=False healthy=False
```

The cause is the stock source set against the hardware actually present:

```
AHRS_EKF_TYPE 3   EK3_ENABLE 1        <- EKF3 is selected and enabled
EK3_SRC1_POSXY 3  EK3_SRC1_VELXY 3    <- 3 = GPS.  There is no GPS on this machine.
EK3_SRC1_POSZ  1  EK3_SRC1_YAW   1    <- Baro, Compass: both fine
GPS1_TYPE 1                           <- auto-detect, finds nothing
```

With horizontal position and velocity both demanding GPS that never arrives, EKF3 never
initialises. Fixed by a ROMFS defaults file, `libraries/AP_HAL_Linux/boards/pi5/defaults.parm`
(waf bakes `boards/<name>/defaults.parm` into ROMFS and points `HAL_PARAM_DEFAULTS_PATH` at it):
`EK3_SRC1_POSXY 0`, `EK3_SRC1_VELXY 0`, `EK3_SRC1_VELZ 0`, `EK3_SRC1_POSZ 1` (baro),
`EK3_SRC1_YAW 1` (compass), `GPS1_TYPE 0`, `ARSPD_TYPE 0`.

Setting these over MAVLink instead was tried and **did not read back** — a baked defaults file is
reproducible and version-controlled, which is what an AHRS rig wants anyway.

## OPEN — the IMU stalls, and this blocks everything above `[measured]`

**The reconfigured build has never been verified, because ArduPilot no longer gets IMU samples.**
Startup stops dead after two lines and never reaches `ArduPilot Ready`, never opens the MAVLink
socket:

```
RPI 5
MPU: temp reset IMU[0] 2114 0
```

`AP_InertialSensor_Invensense.cpp:601`. `_check_raw_temp(t2)` fails, so the driver calls
`_fifo_reset(true)` and returns false — forever. The two numbers are the tell: `_raw_temp = 2114`
is a **sane** temperature (a direct register read gives 2118, ~27.3 C), while the FIFO-derived
`t2` is **0**. The FIFO is returning **zeros**, not desynchronised garbage.

What has been ruled out `[measured]`:

- **Not the sensor.** Direct register reads are healthy — `WHO_AM_I 0x71`, stable accel, sane temperature.
- **Not a stale chip state.** A full `DEVICE_RESET` + `SIG_COND_RST` (`USER_CTRL 0x40 -> 0x00`,
  `CONFIG 0x41 -> 0x00`) changed nothing; the next run stalled identically.
- **Not a competing bus user.** No process holds an i2c fd; no relevant service is running.
- **Not intermittent.** Three consecutive trials, three identical stalls.
- **Not bus speed alone.** i2c-2 is already at 400 kHz (`dtoverlay=i2c2-pi5,baudrate=400000`).

Both of my build-time changes are now excluded — one by test, one by reading the code:

- **`defaults.parm` is not the cause.** `[measured]` Rebuilt with it removed
  (`HAL_PARAM_DEFAULTS_PATH` absent from the generated config, confirmed) and the stall is
  identical: `MPU: temp reset IMU[0] 1976 0`, no `ArduPilot Ready`. The file has been restored,
  since it is correct and simply not implicated.
- **`ROTATION_ROLL_180` cannot be the cause.** `[derived]` In
  `AP_InertialSensor_Invensense.cpp`, `_check_raw_temp(t2)` is evaluated and returns `false` at
  line 601, **before** `_rotate_and_correct_accel()` is reached at line 613. The failing check runs
  upstream of any rotation, so a rotation value cannot reach it.

**So no software change of mine explains it, and no cause is claimed.** It contradicts earlier the
same day: the *identical hardware on the identical bus* reached `ArduPilot Ready` with
`3D_GYRO`/`3D_ACCEL` healthy and `RAW_IMU` carrying real values. With the code excluded, the
remaining candidates are the machine or the wiring. Next step is a power cycle of the sensor rail
and a look at the physical I2C connection — neither doable over SSH.

**Do not read this as "I2C IMUs do not work with ArduPilot"** — `bebop`, `blue` and `disco` all
ship `IMU Invensense I2C:2:0x68`. What is established is that *this* rig stalls in the FIFO path,
and that the class of problem disappears on SPI, which is what every Invensense hwdef uses
(`SPI:mpu9250`). SPI0 is free here: GPIO9/10/11 are muxed `a0`, GPIO7/8 unclaimed.
