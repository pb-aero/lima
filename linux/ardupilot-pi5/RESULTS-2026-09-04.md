## It runs, and it cannot arm — as designed `[measured]`

Startup emits, among the MAVLink stream:

```
Config Error: Baro: unable to initialise driver
Config Error: fix problem then reboot
```

That is `--board=linux`'s `HAL_INS_DEFAULT HAL_INS_NONE` doing exactly what §2 of `NOTES.md` said
it would: no IMU, no baro, no compass declared. The binary is a working MAVLink-speaking
ArduPlane that will refuse to arm. For a bare Pi 5 with no autopilot HAT this is the correct and
only outcome — it is not a fault to chase.

Note also: with no `--serial0` argument the MAVLink stream goes to **stdout**, which is why
running it bare fills the terminal with binary. Real use wants e.g.
`./build/linux/bin/arduplane --serial0 udp:<gcs-ip>:14550`. Full option list from `--help`
includes `--serial0..9`, `tcp:`/`udp:`/`udpin:` endpoints, `--log-directory`,
`--storage-directory`, `--cpu-affinity`.

## Prediction 1b confirmed at the point of use `[measured]`

`NOTES.md` §1b predicted from source that `--board=linux` compiles `Empty::GPIO`, never calls the
Pi-5 detector, and therefore never prints `RPI 5`. Checked against the generated config:

```
GPIO_RPI compiled in : no
  -> Empty::GPIO. No /dev/mem mapping, no pin claims, no Pi-5 detector call.
```

and the startup output contains no `RPI 5` and no `Cannot detect board-type`. Both absences are
correct. **The `strncmp(entry->d_name, "soc", 4)` bug in `Util_RPI.cpp:62` is real and still
unfixed upstream, but this build cannot reach it.** It remains a live hazard for `navio2` /
`pilotpi` / `navigator64` on this kernel, where it becomes an `AP_HAL::panic` at startup.

## The ADAU1860 pins are untouched — and the first measurement that said otherwise was mine

`verify` samples `pinctrl get 18-21` either side of the run. It showed GPIO19 reading `lo` before
and `hi` after, which looks like ArduPilot claiming an ADAU1860 pin.

**It is not.** Negative control — six samples with no `arduplane` process running at all:

```
sample 1: 18:lo 19:lo 20:lo 21:lo
...
sample 6: 18:lo 19:hi 20:lo 21:lo      <- flips on its own
```

GPIO19 is `I2S1_WS`, a live frame clock. `pinctrl`'s level column is an instantaneous sample of a
signal that is moving, so it varies run to run regardless of ArduPilot. The columns that would
actually prove a claim — the **mux** (`a4 // I2S1_WS`) and the **pull** (`pn`) — are byte-identical
before, during and after. Combined with `Empty::GPIO` being the compiled backend, ArduPilot has no
code path that could touch these pins.

Instrument note: my first attempt at this control printed `18:=| 19:=| ...` because I read
`pinctrl`'s `$4` (the literal `|`) instead of `$5`. A control that returns punctuation is not a
result — it is a broken instrument, and it would have been easy to read the null output as "no
change" and move on.

## The side effect: a kernel arrived that nobody asked for `[measured]`

`apt` history, traced to a single command:

```
Commandline: apt-get --assume-yes install build-essential ccache g++ gawk git make wget valgrind
             screen python3-pexpect astyle python3-dev libpython3-stdlib libtool-bin ppp
             g++-arm-linux-gnueabihf
Install: ... linux-image-6.18.39+rpt-rpi-2712 (automatic)
             linux-image-6.18.39+rpt-rpi-v8   (automatic)
             linux-headers-* / linux-kbuild-6.18.39+rpt (automatic)
```

**`g++-arm-linux-gnueabihf` is the culprit** — the 32-bit ARM cross-compiler drags
`linux-libc-dev-armhf-cross` -> `linux-headers-rpi-*` -> `linux-image-rpi-*`, and those
meta-packages pull the current Raspberry Pi kernel, 6.18.39. Both `/boot/firmware/kernel_2712.img`
and `kernel8.img` were rewritten at 17:05.

The irony: **that cross-compiler is useless to this build.** `hwdef/linux` sets `TOOLCHAIN native`;
we compile aarch64 on the Pi. `install-prereqs-ubuntu.sh` installs it unconditionally because most
of ArduPilot's Linux boards are 32-bit cross targets. My `install_ardupilot.sh` skipped the SITL
graphics stack but did not anticipate this, which is a defect in my kit.

State right now:

- **Running kernel is unchanged:** `uname -r` = `6.12.47+rpt-rpi-2712`. Nothing has broken.
- **Next reboot boots `6.18.39+rpt-rpi-2712`.**

**Peter's ruling, 2026-09-04: accept 6.18.39.** No rollback performed.

`[gap]` **Consequence to carry forward:** every ADAU1860 / RP1 I2S result in
`linux/adau1860-pi5/` was measured on `6.12.47+rpt-rpi-2712`. After the next reboot they are
claims about a kernel the machine is no longer running — device-tree node names, `dwc-i2s`
behaviour and overlay compatibility all sit on that version. Re-verify the 4-lane duplex bring-up
on 6.18.39 before trusting it again.
